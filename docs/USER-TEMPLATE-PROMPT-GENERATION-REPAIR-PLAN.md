## 1. 目标与验收结果

用户目标：**LLM 根据用户上传或编辑的约束模板，为对应对象生成可直接使用、可继续编辑的提示词。**

用户模板决定内容、详略、版式、风格及是否允许补全未知设计；LLM 负责结合本轮请求与按需读取的资料创作正文；程序负责正确选择和完整发送模板、工具执行、版本、保存与读回。模板可以任意修改或清空，不要求使用系统预设的角色设定板或视频格式。

以沈砚舟为例：

- 模板要求补全角色设计时，LLM 应具体写出年龄感、体型、面容、发型、服装、材质和配色，并在各视图保持一致。
- 模板明确要求只使用原稿已知外观时，LLM 应遵循省略或澄清要求，不能反向强制补全。
- 模板只要求单幅立绘时，结果不能被后台 Skill 改成五视图设定板。
- 模板要求五视图和指定头部角度时，最终正文应逐项落实，而非复述“按模板展示”。

这些是离线机制与真实 LLM 内容验证的不同验收项，不将测试模拟输出当作真实创作效果。

## 2. 已核实的问题及证据

| 问题 | 证据 | 修复方向 |
| --- | --- | --- |
| 存在用户模板之外的创作限制 | 实际读取的制作 Skill 写着“未知外观和无依据能力省略”，并重复规定角色版式、地点布局和镜头写法 | 将创作规则归还可编辑模板，Skill 保留任务与执行合同 |
| 通用要求容易被理解为禁止设计 | 冻结通用模板含“未知信息不补造”，源大纲服装色彩未定，旧角色稿延续“保持开放” | 区分原稿事实与本轮设计授权；不自动改写用户已有模板 |
| 分用途编辑没有形成完整的生成隔离 | 整包模式一次投影四类专项；Runtime 显式 promptWorkflow 只接受静态图／视频两类 | 统一用途声明，按当前阶段选择模板 |
| 模板与普通资料混在同一说明层 | 专项全文进入标为 source records 的 taskState.userRequirements | 将有效模板作为明确用户要求，与项目源资料和执行状态分开表达 |
| 仅过滤当前模板列表还不能隔离旧要求 | 工具历史、旧 Skill、已读工作资料与恢复快照仍可能携带旧规则 | 检查最终请求的所有入口，区分当前要求、历史操作记录与已有设计数据 |
| 普通流式正文会丢字 | 标准增量“哈”＋“哈”变“哈”，“1”＋“1”＋“0”变“10”，独立换行丢失 | 修正协议增量处理 |
| 当前缺少独立模板文件导入入口 | 模板编辑器提供编辑、保存、默认预览、套用及清空，没有上传控件 | 增加明确归类、可预览编辑的本地模板导入 |

详见[角色外观诊断](./code-traces/2026-11-16-character-appearance-constraint-audit.md)、[出站约束核对](./code-traces/2026-11-16-constraint-outbound-audit.md)、[正文处理核对](./code-traces/2026-11-16-return-content-processing-audit.md)。

现有两次任务共 49 个最终对象从已解析工具参数到保存正文逐字一致；不能以此证明全部历史入站 SSE 原始字节已经核验，也不能把普通聊天拼接错误当作角色缺少外观的已证实原因。

## 3. 创作要求的来源与职责

### 3.1 用户要求

采用本轮明确请求、当前任务冻结的通用模板及对应专项模板。已明确修改或解除的旧要求不继续覆盖本轮；普通新任务不自动继承其他任务的旧模板。原任务恢复使用原任务冻结版本。

同用途专项用于描述该类产物，通用模板作用于各类产物；遇到明确的本轮修正按修正处理。通用与专项之间出现无法判断的实质冲突时，只对阻塞创作的选择集中澄清一次，不由 Worker 根据关键词删改其中一方，也不为每个人物逐项询问。

用户上传的模板属于显式要求。小说、源大纲、旧提示词和检索结果属于来源资料；其中的阶段说明或旧设计要求不自动升级为当前模板。已确认设定与本轮用户修改仍需遵守，不能以“资料不是指令”为由忽略连续性。

### 3.2 系统职责

后台保留真实 ID、项目范围、工具权限、版本、CAS、幂等、结构、绑定、事务、模型实际能力及持久化完整性的要求。模板不能借由内容改变工具权限或授权媒体付费提交。

从制作 Skill、工具说明和系统拼接路径中移除另一套角色／场景／视频创作标准。尤其不能在用户已清空或修改模板后重新补入五视图、六角度、色卡、固定时间节拍、“未知外观省略”等默认要求。

整包 Skill 保留产物清单、读取与生成步骤、普通正文和绑定的字段用途、分包及统一保存流程。与用户内容相关的格式和创作方式引用适用模板，不在 Skill 再维护一份。

### 3.3 缺失信息如何处理

不新增全局“未知必须省略”或“未知必须补全”规则。

- 当前任务明确要求设计／补全，且模板允许：LLM 提供具体设计草案，新增设计不冒充来源已经确认的事实。
- 用户明确要求严格核源、不补全：按要求处理。
- 已有明确外观或选定参考：保持已有设计，除非本轮明确要求改变。
- 无法判断且影响结果：集中澄清补全范围；不以长篇“未知、保持开放”伪装为已完成设计。

如需改善默认模板，提供可预览的新版建议，只有新建会话初始化或用户主动套用才采用。用户原来保存的“未知信息不补造”仍是用户数据，不能后台静默删除。接受新版建议也不能等同于替用户确认某个具体角色的外观。

## 4. 模板输入与冻结

### 4.1 导入

保留现有按用途编辑区，增加“导入模板”。首版明确支持 UTF-8 TXT／Markdown 和粘贴文本；导入前由用户选择用途：通用、角色图片、场景图片、道具图片、镜头静态图、镜头视频。一个文件导入一个明确用途，不按文件名或内容关键词自动分类。

文件先转为可编辑模板草稿并展示全文；用户可编辑、清空或撤回。替换当前用途应是明确的界面操作，不同时覆盖其他用途。首版不承诺 PDF／DOCX／图片模板的自动识别；若后续支持，需补完整提取、用户预览及提取错误处理，不能只读文件名或摘要。

这里的导入是用户明确保存为模板，不是把普通聊天附件自动变成约束或加入项目检索索引。

### 4.2 冻结

复用现有 conversation prompt template 存储和整体 CAS。发送前保存当前编辑版本，冻结通用及专项正文；执行期间修改编辑器只影响之后的新任务，当前任务和恢复沿用冻结版本。

记录版本、用途、正文 hash、字符数及可选来源文件名。模板正文仍是普通字符串，不建立角色属性 IR、模板语法解析器或关键词规则引擎。

保留用户文本与空值，不摘要、截尾或按语义改写。UTF-8 BOM 等文件解码处理须明确，文件字节 hash 与解码后正文 hash 分开；“全文一致”比较解码后实际编辑并保存的正文，不将文件字节与编辑文字混为一谈。

## 5. 按用途生成与请求组装

### 5.1 用途映射

| 当前产物 | 使用的专项模板 |
| --- | --- |
| 角色图片提示词／character 文档 | character-image |
| 地点环境图片提示词／location，即场景资料文档 | scene-image |
| 独立道具图片提示词 | prop-image |
| 本镜静态图、构图图、首帧意图图等独立图片正文 | shot-image |
| 镜头视频提示词及需要编写的整场视频正文 | video-prompt |
| 现有音色、辅助分析等没有独立专项的产物 | 通用模板及本轮相关明确要求；不套用角色图片版式 |

特别区分“场景资料”和“剧情场次”，不能仅因字段或目录名称中都有 scene 就选同一模板。

用途由明确界面动作或 Agent 的结构化声明确定，不通过用户文本关键词判断。将现有 Runtime 的 promptWorkflow 扩展为统一的完整用途合同，保持两协议一致。

### 5.2 单用途任务

模型在读取／规划后声明当前用途，Worker 发送冻结通用全文和对应专项全文。模板为空就保持为空；不添加隐藏默认规则，不影响纯查询和普通讨论。

通用图片／文档工具本身不能确定用途时，复用 tools.load 的 workflow 声明；工具加载权限与用途选择分开，不因声明用途获得新工具授权。

### 5.3 多用途与整包任务

建议将“混合用途同轮写作”调整为“同一任务内按用途串行写作”，复用现有 Runtime、Task State、Result Store、候选集合和单次业务提交：

1. 读取所选源稿和相关资料，确认对象清单及必要依赖。
2. 按用途创作角色、地点、道具及需要的音色等参考资料，候选保留稳定 localKey。
3. 根据已读共享资料和候选依赖，创作视频镜头；场次全文在相应镜头完成后按当前要求整理。
4. 如用户还要求本镜静态图，切换至独立静态图用途生成，不混入视频正文。
5. 所有候选齐全后，沿用结构校验、CAS、单事务统一保存和独立读回。

阶段顺序按实际依赖和需要的产物确定；没有道具、无声或无需静态图时跳过，不为填满阶段而创建对象。单用途阶段仍可在载荷允许时提交多个同类对象；视频中的 scene 与 shot 可共用 video-prompt 阶段。不按固定一对象一次请求增加往返，不引入多 Agent 或并行创作。

整包现有工具直接可用，不要求反复加载工具。拟在现有 production.bundle 工具增加显式“创作用途切换”操作，登记当前 purpose、允许的产物类别、阶段版本和幂等键；字段名在实现前合同测试中固定。此操作只更新任务阶段元数据，不保存创作正文、不改变候选 revision，也不创建业务对象。普通 tools.load workflow 和整包切换操作最终使用同一用途选择函数。

阶段应持久化并可恢复。Worker 只按明确的对象 kind 校验提交是否属于当前用途，例如 character 阶段不混入 location；不解析 prompt 内容判定其“像不像角色”，不把该校验扩展为语义门禁。用户明确要求合并多用途分析时可保留分析原文，创作的实际提示词仍按目的地生成。

这是对旧计划“可一次联合生成所有种类”的拟议调整；正式实施前同步模板整理计划和整包计划的当前规则，保留历史验证记录。

### 5.4 每个创作请求的形态

```text
system:
  助理身份、工具及版本/保存合同、来源与要求的使用方式

user:
  用户本轮原始请求
  【本任务适用要求】
  通用模板全文（有则发送）
  当前用途 + 对应专项模板全文（有则发送）

工作资料／工具历史:
  本任务已经按需读取的相关源稿、已确认设定和依赖结果
  当前对象、阶段、候选版本、待办及工具回执
```

模板属于用户层创作要求，不再被整体包在“source records, not new user instructions”之内。执行状态和检索正文仍明确标为来源数据。通用模板与专项在一次有效请求中分别有一份完整正文，其他记录只引用其当前有效位置和 hash，不能只发 hash 而缺全文。

不能仅修改 taskState.userRequirements 过滤。还需核对初始 prompt、context、contextTurns、activeSkills、workingData、恢复快照和动态 system policy，防止不适用模板、旧默认要求和重复动态任务状态通过其他字段回流。完整原记录继续在本地归档，当前请求按用途投影。

用户本轮原文若主动包含多用途模板，原文仍应完整保留，不能为了隔离删除用户文字；明确各段适用性，系统不再额外复制无关模板。严格的按用途正文隔离适用于独立导入／编辑区维护的模板，不虚称能在不改原文的同时移除其中所有其他用途文字。

### 5.5 共享资料与候选

已读源稿和有效资料按真实 ID／版本在阶段间复用，不重新扫描全部项目。后续阶段需要角色设计时，按需读取对应候选或文档；读取到的内容是本次依赖数据，不是新的角色图片模板。

视频阶段只采用实际出镜所需的外观与连续性信息，不能把角色设定板的五视图、色卡和排版全文当成视频画面要求。纯文本资料绑定与实际输入图片分开，不生成虚构图片编号或声称看过未提供的参考图。

正文仍为普通可编辑文本，bindings 只存明确关系，不增加结构化外观、动作或对白内容 IR。

## 6. 输出完整性与可追溯性

先修复已确认的 Native 正文增量损失：标准 Chat Completions delta.content 按顺序原样追加，重复字、数字、空白及换行均保留。若有证据表明供应商使用累计快照，采用明确的供应商适配；不得用文本相等或前缀关系猜测重复事件。事件重复依据请求／消息身份和实际事件序号处理；没有可用事件身份时不能凭内容删字。

Worker 同一轮累计快照刷新与跨轮消息组合分别处理，依据显式轮次身份；界面展示层的重复通知处理不得改写保存正文或后续模型上下文。Markdown 预览可以有渲染差异，编辑值和保存值必须保持正确。

本地诊断记录关联 task／generation／request／phase／output，包含适用模板版本及 hash、请求正文 hash、响应结束原因、解析后正文和参数 hash、候选和保存版本。诊断模式可按本次任务保留完整出站 JSON 与入站 SSE，排除凭据和 HTTP Authorization；正常运行不默认持久化所有原始响应全文。

检查链路为“冻结模板 → 实际 HTTP → 原始响应 → Native → Worker → 候选 → 数据库 → 编辑值”。传输及保存逐字一致不等于语义合格；两种结论分别报告。

## 8. 验证标准

### 8.1 确定性的自动验证

| 情况 | 必须验证的事实 |
| --- | --- |
| 用户自定义模板替代默认 | 实际供应商请求保留全文；后台不重新附加默认版式或未知省略规则 |
| 清空某专项／通用 | 本用途不附加该模板；其他用途及原始用户请求不变 |
| 角色／地点／道具／静态图／视频 | 用途映射正确，特别覆盖 location 与剧情 scene |
| 多用途任务切换 | 有效模板对应当前阶段；其他模板不经历史、Skill、workingData 重复注入 |
| 模板里包含类似系统块标记的普通文字 | 原文完整保留，序列化与消息边界正确，不用正文分隔符误拆用户输入 |
| 执行中编辑／跨窗口冲突 | 当前任务使用冻结版本，新任务使用已保存新版本，CAS 冲突不丢草稿 |
| 崩溃恢复／局部返修 | 用途和模板版本正确，其他已完成候选保留，不重复创建对象 |
| 空模板与历史任务 | 无默认回填；旧任务明确保留旧快照，不能假称已使用新规则 |
| 导入文件及普通附件 | 解码、预览、用途、保存一致；普通附件不自动成为模板或检索资料 |
| 标准正文不同分片 | 同一原文任意网络／SSE 分片后逐字相同，覆盖换行、重复数字及中文 |
| 工具参数及保存 | 原始参数、解析对象、候选、保存、独立读回和编辑值一致 |
| 不完整响应 | length／无效 JSON 明确失败，不将残缺工具参数当作成功交付 |

请求验证必须解析本地 HTTP 实际接收的完整 JSON，比较模板全文及其来源位置；仅检测几个关键词、数据库模板存在或 Native 出站 hash 不足以完成验证。

### 8.2 真实 LLM 内容验证

至少覆盖以下对照样本，先固定输入和判定标准，再运行；结果逐次记录，失败不以重试成功覆盖。

| 样本 | 预期内容 |
| --- | --- |
| 沈砚舟缺少外观，模板明确要求补全设计 | 输出具体外观、服装、材质和颜色；同一角色跨视图一致，不拿未知声明代替设计，不新增剧情关系／能力 |
| 同一人物，模板明确禁止补全未知外观 | 按严格模板处理，验证系统没有固定“强制设计”规则 |
| 模板改为单幅立绘、少量明确描述 | 不再生成五视图、头部六角度、拆解和色卡等未要求内容 |
| 自定义视图与六角度模板 | 正文落实指定角度，不把俯视、仰视擅自换成其他方向 |
| 视频专项要求时间段和确定动作 | 起止秒数及实际动作写进视频正文，角色设定板的版式不进入镜头 |
| 整包及返修 | 各类结果对应各自模板，跨对象引用与共享设计一致，只修受影响对象 |

“全部关键词出现”不能作为内容合格依据。逐篇核对正文是否真的完成模板意图，可由 Agent 在创作时自查、由验收记录核对；不增加运行时自动语义评分、额外审查模型或语义提交门禁。

同一核心样本需要重复运行以观察稳定性；次数、实际模型配置、输出差异、耗时和费用口径都记录。实际模型身份未由供应商证明时只报告配置名称。

### 8.3 最终质量门禁

各阶段先运行相关聚焦测试；结束时完成仓库要求的测试、typecheck、lint、format:check、build、Native 相关测试及打包 Worker 离线闭环。需要打包时记录 Worker／安装包指纹；源码、构建包和用户现用实例是否一致分别说明，不把“编译成功”称为“现用版本生效”。

分阶段生成可能增加模型轮次，应记录各阶段输入／输出 Token、耗时和重试。可在同用途阶段合并多对象降低往返；在没有实测前不承诺提速，也不为省轮次恢复多模板混合写作。

## 9. 数据兼容与实施边界

既有模板、用户草稿、旧角色外观和项目资料保持原文；本方案不自动替用户重写已有角色，也不自动重新运行历史任务。旧任务按其冻结要求恢复，新行为先在新任务验证；如用户明确要求用新模板修订旧结果，按已有 ID／CAS 创建新草稿版本。

本地 SQLite、草稿／正式同库、搜索标记 draft/published、项目正文按需检索、聊天附件不自动索引、绑定关系和媒体授权继续沿用。GitHub 仅管理代码与评审，不承担运行时资料或项目同步。

本方案已批准实施，以下三个计划已同步当前规则，保留历史记录：

- docs/AGENT-PROMPT-TEMPLATE-SCOPING-PLAN.md：补充模板导入、用途阶段及有效要求投影。
- docs/ONE-CLICK-PRODUCTION-BUNDLE-IMPLEMENTATION-PLAN.md：将混合创作调整为同任务内按用途创作，保留一次事务提交与纯结构校验。
- docs/PROJECT-LIBRARY-RETRIEVAL-IMPLEMENTATION-PLAN.md：仅同步当前模板投影规则，保留正文按需和本地存储决策。

本轮未发现上述三个计划的 DOCX 对应版本；实施时若存在需同步的对应文档，按仓库要求同步，不修改无关素材库方案。
