# Agent 小说创作延迟与工具可靠性专项审计

日期：2026-11-09。采样截止：10:51（UTC+08:00）。状态：保留修复前基线；后续源码修复与验证见文末衔接。

## 1. 结论

当前证据指向四项优先修复的链路缺陷：**章节创建参数合同不一致、章节缺少失败候选复用、失败监督分组过细、续写重复继承会话约束**。另外发现已保存章节直接读回的覆盖缺口，以及模型往返和交付展示方面的改进空间。

小说大纲的 5 分 24 秒主要由正文输出及流程往返组成；第一章的 16 分 50 秒则被失败后反复输出全文明显放大。第二章在审计期间完成，同样出现创建参数错误，说明问题跨任务复现。

本地三次成功保存的 Result Store 调用生命周期分别约 23、20、21 毫秒。未发现本地数据库写入或 Native 准入队列造成分钟级停顿的证据。模型请求窗口包含传输、首包等待和流式输出，不能全部归为模型推理。

这三个样本不足以支持重做 IR。检索成功找到带 `draft` 标记、版本准确的小说大纲和上一章；本次章节提交失败发生在资源定位／创建参数校验，未进入内容 IR 语义处理。

完整脱敏计量见 [evidence.json](./2026-11-09-agent-latency-reliability-evidence.json)。没有导出正文、授权句柄、密钥或 Provider URL。

## 4. 按优先级列出的发现

### F1 / P1：创建与续写共用宽松 Schema，创建规则只在业务层拒绝

位置：`apps/worker/src/agent-tool-definitions.ts:1168,1185`；`agent-draft-submission-service.ts:127,134,136`。

`novel.chapter.write_draft` 在同一 Schema 中允许 `baseVersionId` 为字符串或 null，也允许 existing-target/CAS 字段；创建分支却以 `!== undefined` 判断禁止携带这些字段。工具描述虽已说明创建不应携带 CAS，但 Schema 不能表达动作差异，错误又只返回泛化的 “New chapters cannot specify an existing target or CAS.”，未指明命中的字段及 null 也必须删除。

离线使用运行构建中的 Schema 校验器验证：省略 CAS、携带 `baseVersionId:null`、携带 `expectedChapterRowVersion:1` 三例均通过 Schema；后两例与创建分支的禁止规则冲突。真实两章共六次失败提交中，五次最终报创建 CAS 错误，另一次先被错误 structureNodeId 拦截。

建议：以 action 区分创建／续写合同，按协议能力验证 Schema 支持；业务错误返回结构化字段路径、动作和可执行更正说明。创建时显式说明省略 CAS，包括 null；不要通过静默删除参数替模型掩盖真正版本冲突。

验收：覆盖 create 下 null／真实 CAS 值／错误 locator，覆盖继续／重写所需的版本字段；模拟模型→Schema→业务入口两层贯通，两协议兼容性分别验证。

### F2 / P1：章节未接入失败候选复用，现有更正协议也不能删除字段

位置：`apps/worker/src/agent-prepared-arguments.ts:6,105`；`agent-context-manager.ts:628`。

现有 preparedArguments 工具集合包含文档和场镜写入，却没有 `novel.chapter.write_draft`。大参数会被历史投影改为 `archivedArguments`，模型可以通过检查点重新读取原参数，但下一次章节调用仍需输出完整正文。现有 prepared 合并方式 `{...original, ...corrections}` 只能覆盖字段，不能省略原候选中的 `baseVersionId`；改成 null 仍然触发 F1。因此只把章节加入白名单仍不够。

建议：复用现有 Result Store，将章节候选纳入同一机制，并加入明确、有界、可审计的字段删除／更正能力。更正后照常执行 Schema、授权、资源和 CAS 校验；不自动更新版本，不另建候选存储。

验收：失败后及重启后能引用同任务同工具候选，只删除禁止字段并保留正文 hash；拒绝跨项目／跨任务／错工具／损坏 hash；真实 CAS 冲突必须继续失败。需要真实小说任务证明模型确实使用引用，不能只以存在该功能计入收益。

### F3 / P1：失败指纹包含完整参数，微调无关字段可分散同一失败

位置：`apps/worker/src/agent-context-budget.ts:668,672,725,766`。

失败 key 包含工具名、完整规范化参数和错误内容。正文或 displayLabel、expectedRevision 等变化都会得到新 key。真实第一章结果逐条离线重放后，五次失败的最终分组计数为 `[1,1,1,2]`，每一步都没有触发四次相同失败的停止条件。现有逻辑没有丢失记录，但未能把同一创建错误的无效修复归为一个可监督问题。

建议：保留完整调用指纹用于审计，再增加面向修复的错误分类：工具／动作／目标／错误字段／有关版本状态。正文重发本身不构成这个参数错误的修复进展；真实目标、版本或证据发生变化仍应区分，避免误停有效修复。

验收：本次五条真实失败重放能识别连续无效修复；更正相关字段后可继续；新版本、不同目标、必要的读取和真实保存不误判。不能用缩小总调用硬上限替代错误监督。

### F4 / P1：follow_up 逐级继承整段要求，重复会话约束随续写增长

位置：`apps/worker/src/agent-context-manager.ts:80,443,446,862,867,1100`。

初始化把“会话约束＋本轮请求”作为原始要求。follow_up 从父任务继承全部 userRequirements，重新加上 generation 前缀，按新 id 去重。发送时只排除当前 `original`，所有继承条目的完整文本仍进入 taskState；当前 prompt 又携带同一会话约束。

真实三个任务中，每份要求都含完全相同的 8,547 字符约束：大纲两条要求、第一章三条、第二章四条。路由继承完成后，当前 prompt 加继承 taskState 内的该约束至少分别出现 **2／3／4 份**，尚未计入可能出现在显式历史读取中的副本。

| 样本末轮 | taskState 字节 | taskState 本地估算 Token | 单请求实际输入范围 |
| -------- | -------------: | -----------------------: | -----------------: |
| 大纲     |         28,401 |                    9,099 |      25,414–41,900 |
| 第一章   |         56,315 |                   18,062 |      29,512–74,584 |
| 第二章   |         80,160 |                   25,992 |      28,811–84,178 |

增长还包含其他任务状态，不能将表中全部差额归因于约束副本。缓存可降低部分输入的计费／处理成本，但不能证明重复内容无性能代价。

建议：持久化保留每条原始输入和来源；请求投影中将完全相同、版本一致的会话约束只传一次，其余保留 hash、来源和适用关系。父任务的不同短请求、补充和修改顺序仍保留，不凭模型摘要删除要求，不限制用户输入长度。

验收：大纲→连续多章的同一约束版本不会因 follow_up 链增长而重复传输；约束更改和用户真实重复补充可追溯；重开／恢复后完整原文和语义优先级不丢失。保留用户指定 512K fallback 规划值，不通过放大窗口掩盖重复传输。

### F5 / P2：已保存章节未被直接读回的已知产物校验覆盖

位置：`apps/worker/src/library-search-service.ts:239,252,268`。

`readArtifact` 的已知目标门禁检查计划目标、成功的 `document.submit_draft` 及此前读过的文档，却遗漏成功的 `novel.chapter.write_draft`。第二章已收到包含准确 documentId／documentVersionId 的 draft_saved 回执，ContextManager 也将其登记为 generatedArtifact；随后用这对 ID 直接读回却收到 `LIBRARY_READ_BLOCKED`。

该父任务没有另外登记的文档 artifact/target 行，因而无法通过其他分支补足。此错误发生在已知产物资格判定，尚未到后续 current-version／分支可见性校验，不能归因为版本过期。

建议：从统一的成功提交回执证明已知产物身份，覆盖章节写入；保留同项目、同任务、当前版本、分支可见性和按需发起读取的边界，不放宽任意 ID 直读。

验收：同任务新建章节及重启后可按精确版本读回；跨任务任意文档、旧版本、归档或不可见分支继续被拒绝；读回成功不自动等于语义审查通过。

### F6 / P2：准备、状态维护与收尾消耗过多串行模型往返

位置：真实请求序列，详见第 3 节；工具加载与执行边界在 `agent-provider-tool-gateway.ts:25,217,341`。

大纲四轮模型请求后才开始正文，保存后又经过检查点和最终回复。两章首次正文前分别等待约 172、159 秒，包含目录、检索、工具加载和状态读取。第一章还在已完整读完大纲、`truncated=false` 后，再请求 offset=5440 的空页，对应一轮模型请求约 16.714 秒。

这些读取不全是冗余：续写需要大纲和上一章，检索范围仍由模型决定。现有多读能力已经存在；本轮没有发现多个独立读取合并在同一模型回复中的实际使用证据，不能声称尚未实现并行机制。

建议：复用已确认的路由／工具可用性／有版本的导航事实；在模型已确定需求后组合独立读取。评估把确定性的保存回执、计划数量和状态同步随同一业务结果返回，减少只为登记事实而再次请求模型。保留模型的语义决策及必要审查；先检查成功／失败和未完成项，再给简短完成回复。

验收：相同任务按准备、创作、修复、审查、回复分段比较真实请求数及总耗时；不能删除必要资料读取或审查来制造提速。分页终点应依据 truncated/nextOffset，完整读取后不再探测空页。

### F7 / P2：正文生成主要表现为“参数生成”，保存与任务结束的体验仍混在一起

位置：`apps/desktop/src/ChatPanel.tsx:1837`；`App.tsx:1415,1496`；`agent-resource-refresh.ts:observe`。

现有界面已经显示“正在生成参数”、KB 数及最后接收时间，并非完全没有进度。长正文位于工具参数流，用户难以从这些技术指标判断正在写小说还是等待本地落盘；本次大纲保存后还需等待约 54 秒才结束 Agent。

界面已有每 400ms 轮询及资源变化序号驱动刷新机制，不要求任务完成后才刷新。没有采集到浏览器 paint／文档实际可见时间，不能把这 54 秒直接认定为界面卡住或数据库提交延迟。

建议：按业务展示“正在撰写大纲／章节”“已保存草稿，正在核对”等阶段；评估候选正文预览，明确未保存／已保存边界。继续由提交回执驱动实际文档展示，避免生成中的 JSON 被误当作已持久化正文。

验收：记录首个正文预览、保存提交、界面首次可见和最终答复四个时间点；验证取消、失败／重试、项目切换和刷新失败时不会展示虚假保存状态。

### 9.1 从工具调用推进，转为真实交付物状态推进

审计后的源码复核发现，`apps/worker/src/agent-task-deliverables.ts` 的 `DELIVERABLE_TOOLS` 没有 `novel.chapter.write_draft`；准备参数复用集合及直接读回资格判定也分别遗漏章节。章节保存已有自己的子任务、锁和版本回执，ContextManager 也会记录生成产物，但这些事实没有被每个横向机制一致消费。

因此应在现有任务、Result Store 和执行回执上统一交付物身份及能力声明，让计划、失败修复、读回、审查和完成判定使用同一份事实。领域服务继续负责章节锁、资料类型、资源绑定和 CAS，不新增一套执行器或产物存储。

| 业务事项       | Agent 负责                             | 应用负责                                     |
| -------------- | -------------------------------------- | -------------------------------------------- |
| 用户要做什么   | 理解自由文本、范围、否定和语义冲突     | 提供用户明确选择的表单意图、目标和真实状态   |
| 需要哪些资料   | 判断相关性并按需发起读取               | 返回有版本、有权限边界的目录和正文           |
| 需要交付什么   | 声明开放任务的产物、依赖与内容验收条件 | 校验声明，登记目标及真实完成状态             |
| 撰写和检查     | 创作、内容判断、按合同执行语义审查     | 校验参数、引用、版本和保存完整性             |
| 已经保存了什么 | 使用回执决定后续工作                   | 原子保存、生成回执并同步已有任务状态         |
| 是否交付完成   | 如实报告内容结论和未完成项             | 根据交付覆盖、未决问题与必需审查阻止误报完成 |

不能让模型反复报送系统已经知道的保存事实；也不能由应用根据关键词替模型决定剧情、选资料或给出语义审查结论。

### 9.2 同一执行模型按实际依赖启用步骤

| 场景                   | 建议的必要步骤                                                                     | 可以减少的流程开销                                               |
| ---------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 目标明确的一份新大纲   | 解释要求；需要时取资料；生成候选并完成适用内容检查；校验保存；报告结果             | 不为形式再拆独立计划、保存事实登记和多轮总结                     |
| 基于既有内容续写一章   | 解释续写范围；按需读取大纲／上一章及适用约束；生成候选；保存；执行要求的读回／审查 | 复用真实定位和已加载工具，避免重新浏览同一目录或重复传入相同约束 |
| 多章、跨文档或场镜制作 | 显式产物与依赖；分批交付；检查点与恢复；内容审查；汇总                             | 复用已保存输出，仅继续未完成项或原位修复                         |

这些是能力按需启用的策略，复用统一 Runtime 和提交边界。自由文本仍由模型理解；只有表单明确提供或本任务已确认的事实可以直接复用，不按字数／关键词强行分流。初始看似简单的任务若发现额外依赖、修复或审查义务，应在原任务内扩展，不重建任务或丢弃已有进度。

对于简单交付，评估将最小产物声明与首次业务提交合并，使应用能在同一事务中登记目标和结果，减少只为登记计划的模型往返。该建议需先解决合同完整性、失败恢复和已有接口兼容，不能直接跳过当前完成检查。用户要求或既有合同规定的独立正文读回／语义审查必须保留。

### 9.3 候选生成与提交修复分开

候选正文生成后持久保留，字段、定位或参数错误只修相关字段。版本冲突由模型读取并决定是否重新创作；内容不合格则修改正文。两类修复均复用同一候选和既有结果存储，不把每次调用失败都当作重新写一章的请求。

业务错误应包含明确的错误类别、相关字段、候选引用和下一步可用动作；建议动作不代表已获新的权限，也不自动放宽 CAS。真实第二章两次正文 hash 相同，可用来验收“只修参数而不重新输出正文”的路径。

### 9.4 连续创作继承需求，不复制整段任务历史

会话约束保留完整版本及来源，任务引用适用版本；父任务不同要求、明确决策和已保存产物保持可追溯。请求投影只对完全相同的文本去重。大纲及上一章正文仍由 Agent 按需读取，不因建立“小说创作会话”而自动注入全文。

续写任务需要的是当前适用要求、相关资料证据和真实产物定位；过去任务的全部操作流水可按需恢复。不能通过不断嵌套父任务要求来代替连续性管理，也不能用有损摘要覆盖原始用户指令。

### 9.5 区分生成结束、保存成功、内容核验和用户审阅

交付状态应分别展示“正在创作”“草稿已保存”“内容核验中／未完成”“待用户审阅”。最后一句聊天回复不应成为草稿可见的前置条件；`waiting_review` 不应展示成仍在生成。保存失败、内容检查未通过、用户尚未审阅属于不同业务事实，不能共用一个笼统的未完成状态。

已保存及等待用户审阅的草稿仍是草稿，Agent 不发布、不取消发布。复杂任务尚有未交付内容时，即使某个草稿保存成功也必须继续执行或明确报告阻塞。

业务优化的收益首先是减少重复推理、重复正文输出和无效状态往返。这次大纲的主生成请求自身仍用了 219.222 秒，即便消除生成前后约 105 秒的全部开销，也无法据此承诺一分钟完成；剩余输出速度需另行测量和优化。
