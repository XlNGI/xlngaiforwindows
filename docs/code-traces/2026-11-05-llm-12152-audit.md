# LLM 响应流 Windows 12152 审计

日期：2026-11-05。范围：本次截图的模型响应流失败、任务终止和恢复路径。仅审计，未修改生产代码或项目数据，未重放失败任务、未调用真实模型。

## 结论

本次不是此前的 Windows 12029 连接失败。Windows 12152 是 `ERROR_WINHTTP_INVALID_SERVER_RESPONSE`；错误出现在已经收到成功 HTTP 响应头和部分工具参数之后，WinHTTP 继续读取响应体时失败。本地模拟证明非法 HTTP 分块长度、缺失结束分块均可产生同样错误，但实际记录不足以区分供应商入口、上游响应、代理或其他中间链路，也不能证明是哪一种分块错误。

没有证据表明这次是本地超时、用户取消、上下文超限，或 SSE JSON 解析报错。前次匿名连接探测收到 HTTP 403，只说明探测当时能够收到 HTTP 响应，不能验证此次长流请求。

## 审计发现

### F1：断流后整轮终止，缺少自动从暂存进度恢复的路径

影响优先级 P1，属于恢复能力缺口，并非应当取消的防重放保护。

- `apps/worker/src/native-provider-bridge.ts:405` 明确禁止收到正文、思考、工具参数或 usage 后自动重放；自动重试仅覆盖没有输出的 HTTP 500 / 502 / 503 / 504。
- `apps/worker/src/pi-conversation-runtime.ts:1087` 只对明确的无效 / 截断工具 JSON 开启输出修复；普通网络读取错误不进入该分支。
- 同文件 `:1132` 将错误直接终止为整轮失败。
- `apps/desktop/src/ChatPanel.tsx:1052` 的恢复入口是填写继续指令、创建新任务；不是在当前任务里自动恢复当前场景阶段。

因此，即使前 34 次模型请求已经成功，第 35 次中断也会终止整轮。暂存数据没有丢失，但未完成生成需要额外一轮新任务来接续。

后续应明确区分“重放失败 HTTP 请求”和“读取持久化进度后重新规划剩余任务”。后者需要核对 stageId、当前版本、缺失镜头和已保存回执，重新授权，限制恢复次数并正常记账；不能将半截参数当作完整工具执行，也不能无条件重跑整个请求。

### F2：普通传输错误缺少终态统计，难以定位实际断流

影响优先级 P2，代码缺口可直接确认。

- `apps/desktop/src-tauri/src/llm_stream.rs:1444` 与 `:1466` 分别调用 `WinHttpQueryDataAvailable` / `WinHttpReadData`，失败时却都返回同一条文字，无法区分失败 API。
- 同文件 `:1455` / `:1482` 使用 `transport_failure`，没有附带已有的累计接收字节、SSE 事件数、最后有效进展、参数计数、完成标记或已获得的响应 ID。
- 同文件 `:1635` 的超时错误已经有统计，普通读取错误没有使用同等诊断。
- 同文件 `:1491` 只在首个块发出 `received_bytes`，因此数据库中的 600 字节不能用于判断后面是否仍在持续收流。
- `apps/worker/src/provider-request-ledger.ts:80` 只保存 `firstSeen`，无每阶段最后进展时间。内存中的活动时间不能替代失败后的持久化证据。

后续应在失败分支保留 WinHTTP 原始错误码和调用阶段，写入有界、脱敏的最终累计统计及最后有效进展时间。传输错误不应仅凭 `PROVIDER_FAILED` 就被解释为供应商业务错误；日志需要保留其发生在本机传输层的事实。

### F3：界面没有区分连接失败与响应中途失败

影响优先级 P2，用户可见问题。

`apps/desktop/src/ChatPanel.tsx:1449` 处理了 HTTP 状态、额度、格式、调用预算等错误，但没有 WinHTTP 12029 / 12152 映射，`:1507` 直接回传英文。界面没有说明请求是否已经开始返回，也没有结合暂存状态说明仍有哪些部分可恢复。

后续应显示准确的中文状态，如“模型响应传输中断，当前提交未完成”，保留技术详情，分开展示已正式保存、仅暂存、尚未完成的部分。不能暗示取消、保存成功或必然是用户网络问题。

### F4：缺少实际 HTTP 分块异常的回归覆盖

影响优先级 P2，测试缺口。

现有原生用例覆盖正常 chunked 响应、协议完成后不等待连接关闭、空闲 / 总超时、取消和 SSE 截断；没有非法 HTTP chunk 长度或缺失终止分块的集成用例。Worker 的事件测试覆盖不重放部分输出，但没有验证“实际 WinHTTP 分块错误 → 精确失败诊断 → 已暂存状态可接续”的完整链路。

后续应补充本地 Provider 用例，断言原始错误与进度保存正确、错误不会变成用户取消、半截工具不执行、已提交内容不重复；不应把异常 EOF 改判为成功。

## 额外运行效率观察

35 次请求中，`tools.load` 8 次，`conversation.task.checkpoint` 11 次（6 次保存、5 次读取），`project.get_context` 3 次。还有 1 次路由调用因目标任务无效被拒绝。直到第 33 次请求才创建场景暂存。

这说明写入首个镜头之前已有较多准备、交接和恢复开销，会增加等待与暴露于传输故障的机会。仅凭次数不能判定每次都是错误或无效重复，也不能把它认定为 12152 的直接原因。应另以工具参数、阶段交接和预算变化做受控复现；不应直接扩大上下文窗口、删除用户资料或放宽循环保护。
