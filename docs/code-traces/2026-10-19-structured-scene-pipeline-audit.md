# 2026-10-19 场次结构化参数链路审计

## 结论

用户假设：加入站位、人物状态等结构化要求后，整条链路没有同步处理完整，导致参数不完整。

审计结论是部分成立。站位、初始状态、结束状态及显式连续性事实已经接入合同、审核、SQLite、读取和提示词编译；隔离验证能完整读回。主要缺口位于大型结构化输出的生成、错误处理、入口合同一致性及正文与结构的合并规则。新增结构化要求显著增加了输出复杂度，使这些缺口更容易暴露。

当前日志没有保存失败调用的原始参数与每轮原始结束原因，不能确认那一次究竟是 JSON 截断、模型直接返回空对象，还是完整 JSON 缺少必填字段。不能将下述可复现缺陷直接等同于当次唯一根因。

本次仅审计并新增本报告；未修改功能代码、重启应用、写入用户项目或请求真实模型。

## 检查范围与正常链路

读取了制作执行计划、P6 完整场次要求、镜头连续性计划及相关验证记录。当前流程为：

```text
Agent 工具 JSON Schema
  → 模型流式输出工具参数
  → Rust SSE 累积与 Native host 转发
  → NativeProviderBridge 解析参数
  → Pi 工具参数校验
  → beforeToolCall / Worker 工具授权与审计
  → SceneStructureSubmissionService / EpisodeStructure 解析
  → ChangeSetService 待审核结构
  → 批准后 ProductionService / SQLite 指令版本
  → 场次共享设定与逐镜头编译
  → 制作表单参数投影与提交前来源检查
```

| 检查点 | 实际结果 |
| --- | --- |
| 字段定义 | `subjects[].position/initialState/endState`、`continuity.before/after/locked` 均有 Schema 与类型 |
| Native → Pi | 合法参数在 Responses / Chat Completions 两种桥接配置下逐字段一致 |
| 待审核结构 | 站位、状态及连续性原值均保存；批准前无场次业务写入 |
| 批准、读取及重开 | 实际临时 SQLite 读回的 subjects 与 continuity 和输入完全一致 |
| 最终制作提示词 | 场次编译包含站位、初态、终态、结束事实和首帧描述，所测模型编译 issues 为空 |
| 表单接入 | `use-production-instructions.ts` 接收 `compiled.parameters`，保留人工覆盖；提交前重新编译并检查来源 |

最后一项为代码核对与既有制作集成测试证据，本次没有对真实媒体 Provider 发起请求，也没有新做浏览器验收。

## F1 · P1：截断参数被当作空参数，结束原因也不能可靠阻止执行

位置：`apps/worker/src/native-provider-bridge.ts:440,473,591`；`apps/desktop/src-tauri/src/llm_stream.rs:1330,1351,1929`；`apps/desktop/src-tauri/src/lib.rs:3215`。

- `parseArguments` 捕获 JSON 解析异常后返回 `{}`，既不报解析错误，也不保留该处的失败证据。
- Native 的 `ToolCalls` 事件没有携带原始结束原因，host 转为 Pi 事件时统一设置 `tool_calls`。SSE 的完整协议结束不等于工具参数 JSON 完整。
- 即使直接给桥接层传入 `finishReason: length`，只要消息有工具调用，`applyPiEvent` 仍优先设置 `stopReason: toolUse`。
- 两种协议配置的离线复现结果相同：把一份合法场次 JSON 去掉最后一个 `}` 后，得到 `arguments: {}`、`stopReason: toolUse`、无 `errorMessage`。模拟直接传入的 `rawStopReason: length` 也没有阻止上述结果。

这不是站位字段在序列化时被过滤，而是整份参数一旦解析失败，就丢失了全部已生成字段。修复应保留原始结束原因、区分不完整 JSON 与 Schema 缺字段，禁止以空对象替代失败的解析，并为修复次数设独立上限。

## F2 · P1：Pi 校验失败没有进入 Worker 审计，还会回传完整大参数

位置：当前锁定依赖 `@earendil-works/pi-agent-core@0.84.3/dist/agent-loop.js:404`、`@earendil-works/pi-ai@0.84.3/dist/utils/validation.js:306`；接入点为 `apps/worker/src/pi-conversation-runtime.ts:246`。

Pi 先执行 `validateToolArguments`，成功之后才调用本项目的 `beforeToolCall` 和工具执行器。因而校验失败时，Worker 的工具审计、liveActions 和业务工具预算计数都不能覆盖这个失败；最终会话仍受通用 turn 上限约束，但没有专门的同类参数错误修复次数控制。

Pi 的默认校验错误包含 `Received arguments:` 加整份格式化 JSON。离线模拟 22 镜头参数，仅删除第一个镜头的必填 `stillFrame`：

| 指标 | 结果 |
| --- | --- |
| 输入参数 JSON | 132,796 bytes |
| 产生的错误文本 | 148,818 bytes |
| 是否包含第 22 镜的全部参数 | 是 |

这份错误作为工具结果进入模型后续上下文。它没有经过本项目 Gateway 中对成功执行结果的有界序列化处理。应在 Pi 接入层统一收敛错误，只返回字段路径、原因与必要摘要，同时记录校验失败事件和参数长度；不能靠修改依赖安装目录作为正式修复。

## F3 · P1：原始正文与结构化指令存在两个输入源，保存时正文被覆盖

位置：`apps/worker/src/episode-structure.ts:70,135`；`apps/worker/src/change-set-service.ts:176`。

解析器只在未提供 `videoPrompt/prompt` 时用 instruction 渲染正文；但 ChangeSet 创建时，只要有 instruction，就重新渲染并无条件覆盖 `item.videoPrompt` 或 `item.prompt`。

隔离复现同时提供正文专属标记及合法结构：待审核提案中的两个正文标记均消失，结构化站位标记仍存在。这意味着模型在正文中写了丰富站位／状态，而 instruction 中没有同步写入时，正文里的细节可能在保存时丢失。此问题不解释 JSON 为什么不完整，但属于用户怀疑的“整条链路处理不完整”。

既有工具说明还要求修改绑定时保留正文，因此必须明确唯一内容来源：结构为主时应让模型只提交结构并由系统渲染，或对同时提交的正文冲突做显式处理；不能静默取其中一份。纯关系修改应复用原有正文和结构。

## F4 · P2：工具 Schema、实际解析器与更新场次路径不一致

位置：`apps/worker/src/agent-tool-definitions.ts:250,308,497`；`packages/generation-adapters/src/production.ts:100`；`apps/worker/src/episode-structure.ts:66`。

| 输入情况 | Pi 工具 Schema | 直接进入实际解析器 |
| --- | --- | --- |
| 完整 v2 场次／镜头 | 接受 | 接受 |
| 仅遗漏镜头 `stillFrame` | 拒绝 | 接受 |
| 场次用 `visual.style` 指定风格，省略 `style` | 拒绝 | 接受 |
| 已有 `sceneId` + CAS，仅改绑定、`shots:[]`，不重写 instruction | 拒绝 | 也拒绝，并提示“新场次”必须提供 v2 |

最后一种正是工具文字说明支持的关系修订形式。详细结构要求没有按新建、创作修订、关系修改分开。结果是模型要为简单关系操作重写整份结构，增加漏字段机会，并与 F3 的正文保留风险叠加。

应使用各入口共享的合同与验证，明确不同操作所需字段。已有数据更新需要保留真实 ID、CAS、审核和原指令，不能靠补空值或猜测正文填充必填结构。

## F5 · P2：结构化扩展增加了负担，各层容量限制没有统一

历史对照为引入制作结构前的提交 `8189488` 与当前源码中的同名工具，未修改或切换工作区：

| `scene.submit_structure` | 历史 | 当前 |
| --- | --- | --- |
| 工具定义 JSON | 3,301 bytes | 23,691 bytes |
| 其中参数 Schema | 1,976 bytes | 21,645 bytes |

工具定义约为原来的 **7.2 倍**。新场次和每个镜头都要提供 v2 instruction；人物、状态、节拍和连续性随镜头重复输出。工具描述及系统提示仍要求完整正文与完整结构，未明确避免重复表达。新结构本身有用途，但需要相匹配的分段生成、共享设定、大小估计和失败恢复策略。

另有两项边界已离线复现：

- Schema 允许最多 20 场、每场最多 30 镜；ChangeSet 最多 100 个总条目。4 场各 26 镜（共 108 条）通过 Pi Schema 和 Episode 解析，进入 Worker 后才以 100 条限制拒绝。
- 单个结构文本字段允许 4,000 字符，但渲染后的单场／单镜提示词上限为 20,000 字符。多个合法字段合并后可超过该限制；未显式提供 prompt 的样例仍收到“prompt must be between 1 and 20000 characters”，未说明来自结构渲染超限。

批准执行制作清单已有每 30 项分批处理，**不是**所有超过 30 项的提案都会失败。Native 参数累积和 sidecar 信封分别有 2 MiB 等硬限制，超限处理会报错，未发现它们悄悄删去站位／状态字段的证据。

本次实际失败方案为 4 场、约 16 或 22 镜，低于 100 条限制；上述容量不一致是可复现的额外缺陷，不能当作那次失败原因。

## F6 · P2：大结构输出的进度与输出设置没有完整接入

位置：`apps/desktop/src-tauri/src/llm_stream.rs:2160`；`apps/worker/src/pi-conversation-runtime.ts:620,716`。

Native 会持续收集工具参数，完整响应结束后才通知 Pi；长时间生成结构时缺少可见进度。Pi 模型元数据的 `maxTokens: 16384` 和 `thinkingLevel: off` 也没有映射到 Native 请求体，不能将当次失败解释为“应用固定 16K 输出上限导致截断”，也不能确认远端采用了什么默认输出上限。

应按 Provider 实际能力传递并记录有效设置；对仍在接收参数的长输出展示真实进度，与网络停滞、Schema 拒绝和业务保存失败分别呈现。

- 已有聚焦测试：两协议普通场次提交／审核、完整场次制作、Native → Pi 映射，共 4 项通过；未把未运行用例计为通过。

- 临时项目已关闭并清理；真实 Provider 请求数为 0。本次没有声称验证了真实模型对完整 16／22 镜方案的生成成功率。
