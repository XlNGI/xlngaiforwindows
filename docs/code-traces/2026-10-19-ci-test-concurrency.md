# Windows CI 测试并发修正

## 问题与调整

PR #2 的合并检查发现，Windows GitHub Actions 在默认递归测试并发下，多套 Vitest 同时创建各自的工作进程，SQLite 迁移及大数据检索测试出现资源竞争。`46c2391` 的 push 运行 `39190923116` 有 8 项测试超过 5 秒；已在 main 的 `d4a31d8` 运行 `39183972333` 同样在 5000 条以上检索数据用例超时。

根目录 `pnpm test` 继续先准备本地 FFmpeg 并构建工作区依赖，随后按包顺序执行测试，每包设置最多 2 个、最少 1 个 Vitest 工作进程。测试范围、断言及现有超时阈值保持原值。单个用例内部显式创建的并发任务继续执行，覆盖多项目隔离、共享执行容量与取消行为。

## 验证

- `pnpm test`：完整入口通过，1566 项 JavaScript/TypeScript 测试全部通过；Worker 64 个文件、807 项测试在 121 秒内完成，持久化 17 个文件、73 项测试通过，大数据检索用例在约 2.57 秒内完成。
- `pnpm exec prettier --check package.json`、`git diff --check`：通过。
- 本次只调整测试入口的执行调度，产品代码及模型调用参数没有变更。

远端完整 CI 结果以 PR #2 对应提交的 GitHub Checks 为准。

## 大数据用例的夹具构建修正

`49d2a7f` 的远端运行 `39191745577` 中，桌面 483 项与持久化 72 项通过，仅大数据检索用例仍超过 5 秒。检查发现夹具循环 5001 次执行 `INSERT ... SELECT`，每次都重新查询不断增长的同一张表。局部计时显示原本地用例约 2.51 秒，其中重复构建约 0.98 秒，查询断言约 1.20 秒。

夹具改为 SQLite 单条递归 CTE：先物化读取一次种子分块，再生成同样的 5001 条新分块。保留真实磁盘数据库、全部 FTS 触发器、索引、检索及去重断言，并增加插入数量等于 5001 的检查；现有 5 秒超时保持原值。修改后的整个检索测试文件 13 项通过，该用例约 1.49 秒。生产检索逻辑与数据库结构未作调整。

`pnpm --filter @ai-video/persistence test -- --maxWorkers=2 --minWorkers=1`：持久化包 17 个测试文件、73 项全部通过；修改文件的 ESLint、Prettier 与 diff 检查通过。

## 持久化文件之间的磁盘竞争

`cb12e96` 的 push 运行 `39192701842` 已通过上述大数据用例，但另外两项真实磁盘迁移／仓储用例出现 5 秒超时。同一包仍有两个工作进程同时进行 SQLite 迁移与写盘，表现为失败用例随运行而变化。

持久化包单独启用 `--no-file-parallelism`，在包内按文件顺序执行，其他包继续使用根入口的两个工作进程上限。用例内部显式的并发、事务回滚、迁移重试与锁竞争仍照常运行；测试集、断言与超时阈值保持原值。

本地通过根入口相同参数运行持久化包：17 个文件、73 项测试全部通过，耗时约 26.34 秒；Prettier 与 diff 检查通过。
