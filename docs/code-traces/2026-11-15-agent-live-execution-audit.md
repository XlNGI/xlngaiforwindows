## 优先发现

### P1：缺少读回核验时，仍能通过“下一步”表单宣告完成

最后一个工具调用是 `conversation.ask`，标题为“设定与镜头绑定已完成，下一步？”。前一个调用确实成功更新 13 个镜头。但当前 Task State 的 `bind-shots` 仍为：`persistedCount=13`、`savedCount=0`、`unreadTargetIds=13`、`deliverablesVerified=false`、`nextAction=review_outputs`。没有证据证明这些绑定丢失；未完成的是保存后的当前版本读回核验。

代码依据：`apps/worker/src/agent-task-deliverables.ts` 的 revise 分支要求当前版本读回；`apps/worker/src/agent-provider-loop-service.ts` 在 `conversation.ask` 返回 `awaitingUserAnswer` 时直接进入 `waiting_review`。真正缺少用户信息时需要允许提问，但完成后选下一步的表单不能替代尚待执行的核验。

建议：在任务完成边界和询问下一步边界统一检查交付状态。对于可由工具自行完成的 `review_outputs`，先读回并确认现有 ID、版本、正文与绑定；真正需要用户决策时保留提问能力，准确展示尚未完成的步骤。不能直接把状态改为已完成或取消读回义务。

### P1：多次发出批处理合同禁止的调用，完整正文反复生成后被拒

本任务失败回执共 29 条，其中：

- 9 条属于同一轮超过八个读取的整批拒绝。
- 16 条文档写入以及 2 条状态／导航调用被混合或多写批次合同拒绝。
- 1 条文档参数包含不支持的 `revision`。
- 1 条缺少明确输出身份，命中已保存输出的幂等冲突。

16 条写入批次拒绝发生在四轮，模型分别发出 5、5、4、2 个文档写调用。拒绝是现有安全合同的正常结果，问题在于调用策略反复违约，并且已生成的候选正文没有直接进入有效保存流程。

代码依据：`agent-provider-tool-gateway.ts` 的整批预检限制最多八个只读调用，并禁止混写；`apps/desktop/src-tauri/src/llm_stream.rs` 两协议只要工具集中存在一个只读工具，就设置 `parallel_tool_calls=true`。因此同时可见读写工具时，供应商层仍允许模型输出多个写调用，之后才由 Worker 拒绝。

建议：写入阶段明确使用单调用策略；读取阶段保持受控批量，并在请求说明中展示实际批次上限。保留 Worker 的独立复验。失败恢复应按同任务、同工具、同候选 hash 复用已保存参数，逐个重新校验授权、输出身份和 CAS，不允许未经验证自动执行整批写入。

### P2：多份同类新文档的输出身份未在第一次写入前明确

第一份角色文档不带 `outputKey` 即保存成功；第二名角色同样不带输出身份，命中 `output:implicit:document.submit_draft:character:`，返回“Output already committed; revise the saved object with current CAS.”。后来重新登记逐项计划，并提供各自 `outputKey/outputIndex` 后成功。

代码依据：`apps/worker/src/agent-business-execution.ts` 未指定计划身份时，兼容键由工具、文档类型和 bindingRole 组成，不能区分同一任务中的多名角色。直接引入标题作为身份会破坏现有幂等与改名语义，不应这样修。

建议：计划登记返回稳定、逐项的输出槽位，并在多份同类文档的 schema／工具指引中明确需要选择哪一槽位。错误需清楚区分“同一输出重试”和“另一个计划输出缺少身份”，保留已保存文档 ID 与 CAS。

### P2：高频上下文整理和重复加载工具值得独立优化

53 轮中整理 48 次；前 50 轮已加载工具 7 次。Task State 和已读资料增大后，64K 的旧过程整理目标频繁触发，容易让近期失败规则和当前动作退到较短历史之外。但已读正文不能再次被驱逐；本轮没有证明整理必然导致每次重复加载。

建议：按当前步骤保留必要资料、已加载工具集合、最近错误规则及已保存输出映射；对软整理目标加入增量触发或滞回机制，避免不可释放基线已经超过目标时每轮重复整理。以成对回放比较轮数、错误次数、输入量和恢复完整性，再决定阈值，不直接提高空转保护上限或扩大模型窗口。
