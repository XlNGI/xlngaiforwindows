## 已复现的正文处理错误

当前 Native 的 `apps/desktop/src-tauri/src/llm_stream.rs:2444` 将每个 Chat Completions `choices[].delta.content` 送入 `coalesce_visible_delta`，没有直接保留每个增量。该函数在 `:2510` 清除独立换行，并在 `:2540` 将等于已积累文本或属于其前缀的片段当作重复内容丢弃。它试图兼容重复／累计快照，但仅凭文字内容无法区分正常的重复字与重放。

实际本地 HTTP 接收链路得到以下结果；JSON 形式中的 `\n` 表示真正的换行：

| SSE 中依次给出的正文增量 | 应得到的正文 | Native 实际输出 |
| --- | --- | --- |
| `"甲"`、`"\n\n"`、`"乙"` | `"甲\n\n乙"` | `"甲乙"` |
| `"哈"`、`"哈"` | `"哈哈"` | `"哈"` |
| `"1"`、`"1"`、`"0"` | `"110"` | `"10"` |
| `"哈哈"`，单个增量 | `"哈哈"` | `"哈哈"` |
| `"\n\n"`、`"正文"` | `"\n\n正文"` | `"正文"` |

相同文字“哈哈”仅因 SSE 分片方式不同就得到不同正文，证明这不是 Markdown 预览折叠换行导致的视觉差异。错误发生在 Native 发给 Worker 之前；Worker 的 `native-provider-bridge.ts:648` 继续按收到的增量拼接，无法恢复已丢失的字。被修改过的 assistant 正文也可能进入后续模型上下文，其间接影响尚未通过历史原始响应证明。

每组同时以 1／7／113／8192 字节分割网络输入测试，结果一致，排除了中文 UTF-8 被拆成多个网络字节块所导致的误判。Responses 的 `response.output_text.delta` 走直接转发路径，没有调用这个函数；本次实际配置使用的是 Chat Completions。

既有 Native 测试明确要求丢弃重复／累计正文及纯换行，因此这些测试通过不能证明标准增量正文完整。修复应先保留标准协议的每个增量；若某供应商确实返回累计快照，应通过明确的适配方式处理，不能仅凭正文前缀猜测。

## 制作提示词正文的核对结果

本任务的制作正文来自 `production.bundle.submit.arguments.prompts[].prompt`，而不是普通聊天的 `delta.content`。实际链路为：

```text
SSE delta.tool_calls[].function.arguments
→ Native 按原顺序追加参数片段，完成后校验 JSON
→ Worker 从完整 argumentsJson 解析工具对象
→ prompt 原文映射为文档 contentMarkdown／场次 prompt／镜头 prompt
→ 不可变候选 → 保存清单 → SQLite → 界面输入值
```

Native 在 `llm_stream.rs:2487` 追加工具参数时不调用正文去重函数。超限、无效 JSON 或 `length` 等不完整结束会报错，相关代码没有截去一部分后继续执行。Worker 在 `native-provider-bridge.ts:697` 以完整 `event.call.argumentsJson` 为准解析；进度用的参数增量不是最终保存依据。`production-bundle-submission.ts:14` 按种类选择字段，正文保持原样；`production-bundle-service.ts:240` 起保存后由 `:483` 独立读回。

逐字核对覆盖以下样本：

| 样本 | 最终保存对象 | 解析后工具参数 → 执行参数 → 候选 → 保存清单 → 数据库正文 |
| --- | ---: | --- |
| 上一轮真实复测 `327215d4-820e-49f8-b5ce-f38ded2595af` | 24：12 个参考文档、4 场、8 镜 | 24／24 一致 |
| 用户原任务快照 `973acb94-e79a-4637-806c-01a91febbca3` | 25：12 个参考文档、4 场、9 镜 | 25／25 一致 |

原任务提交过 26 个正文版本，其中末镜后来更新过一次；最终有 25 个对象。加上复测共 50 个提交版本，均在不可变候选中找到相同正文。两次任务的 6 份音色试音文字也与候选、保存清单和数据库逐字一致。

上下文压缩后，有 5 份较大的工具参数快照变成 `archivedArguments` 读取凭据。本次按调用 ID 找到压缩前完整 assistant 参数，逐项验证凭据指向的归档参数和 `expectedHash`；这些引用没有覆盖或删掉原正文。审计脚本首次把同一调用的压缩后引用也当成新完整参数比对而失败，修正为核对完整快照及引用后通过，没有为通过审计修改产品逻辑。

本次复测的 8 个镜头在保存的、已经解析好的工具参数中就没有相对秒数动作段，候选和数据库也保持原样。用户原任务的 9 个镜头含相对秒数，保存后同样保留。因此，已发现的普通聊天正文拼接错误，尚不能解释复测中这 8 个镜头缺少动作时间段。
