# Revision 11 提交合同与长验收回执修复

源码与离线机制已经修复；真实业务闭环仍失败。[本次真实复验](./2026-11-10-one-click-bundle-revision11-real-acceptance.md)使用的是补回执前的冻结构建，不能用终态后补丁的测试结果覆盖真实失败。

## 输出合同

- 新任务使用 `production.bundle.submit` 的扁平角色、地点、道具、音色、辅助文档、剧情场次、镜头集合。未涉及的集合可省略，区分地点和剧情场次；音色必须有试音文本，剧情场次必须有正文，镜头必须有 timing。
- Worker 只补固定 IR 元数据，不创作正文、不按名字猜绑定。模型显式 complete 后，从实际候选机械生成清单；候选提交与封包复用同一事务。
- 分包、幂等重放、CAS、旧修订重放、局部返修和回滚受保护。prepared 参数只允许模型明确的 JSON pointer 修改，禁止更换任务、partKey、operation 或 CAS，防原型污染。
- 完整原始要求和机械分段单元一起保存在原 Result Store；单元保留原文位置、hash 和父 ID。对 Worker 单元可以省略重复抄写 requirementQuote；通过判断仍须是模型提交且有该目标正文证据。显式不适用分组只机械展开，不代模型判断适用性；保留每目标全要求覆盖和最多 1,000 条展开评估。
- 授权回执消耗后继续保留精简新版 schema，revision 10 存量任务保留旧合同；按钮请求、Skill 及原历史请求分别记录。

## 真实失败后补修

真实输入得到 102 条要求，但工具回执集合上限为 100。结构上合法的要求因此使状态读取失败，后续完整长评估也可能因回执太大而回滚。修复只改变传输，不提高全局限制、不删除要求或放宽验收：

1. `bundleCheckPage` 对要求 ID、引用、ready targets、未读来源、问题和错误分别按同一 offset 返回 20 项，附完整计数、下一页和全快照读取定位。分页末尾仍能读到第 101／102 条。
2. `state.records` 中的 pending 使用同一个有界投影，避免另一处重复泄漏完整列表；已分页状态不重复分页。状态判断复用正式 registry，同时检查嵌套集合与 UTF-8 字节，仅尺寸错误进入持久分页，其他策略错误仍抛出。
3. `taskCheckpoint review` 在原工具事务内，先按实际 provider call ID 保存完整评估事件，再返回有界回执。Runtime 不用小回执覆盖权威证据，reviewHistory 继续读取完整事件。
4. 小于 6,000 字符但嵌套集合过长的结果也会外置；回执中仍过大的字段明确列入 externalizedFields，按原 resultId／hash 读完整内容。完整评估不会静默截断。

## 验证与边界

两协议的真实临时 SQLite／授权工具循环验证：102 条要求及全部引用逐页无遗漏；缺最后两条评估被拒，业务实体仍为 0；816 条完整模拟评估持久化，后续审查状态读取其完整覆盖；长事件按 hash 读取尾页，最后 commit → 必要独立 readback → completed。测试语义结论为明确的模拟输入，不能当作真实模型内容验收。

其余回归包括完整单元覆盖、原文及 UTF-16 边界、稀疏提交、结构拒绝、封包原子性、prepared 修参、旧版兼容、CAS／发布／时长保护、事务回滚、失联重开及独立读回。最终门禁、日志和新源码／Worker 身份见[验证 JSON](./2026-11-10-one-click-bundle-revision11-output-contract-verification.json)。

本次没有继续修改验收业务逻辑：模型仍需后续轮次判断内容、逐目标覆盖原要求、提交精确证据；程序只管结构、来源、版本、事务及读回。没有追加付费复验，没有安装或替换用户实例。P2／P3 的真实可修复性、P7 真实内容和完整闭环仍未完成。

## 需要收敛的设计

102 条要求对 21 个目标形成 2,142 组关系，许多只是“不适用”说明。当前机制验证这种合同可执行，无法证明合同高效或模型不会漏判。后续应先由模型声明原要求的适用目标，再审相关正文与跨对象一致性；完整性不能退化为只认模型自报 checklist，结构／版本保护、事务和独立读回继续保留。这是待定收敛建议，未混入本次回执补丁。
