## 原因与代码证据

### 1. 阶段交接频繁打断准备流程，模型交接后继续加载与导航

`apps/worker/src/pi-conversation-runtime.ts:964` 起，根据输入预算、阶段历史至少 4096 Token、存在工具结果及预计交接节省至少 4096 Token，要求交接。触发后 `:1000` 起只向模型提供检查点工具；`:452` 起也会阻止其他工具执行。`apps/worker/src/agent-task-context.ts:354` 明确要求该轮单独保存交接，不能继续读写或结束任务。

现场可见 14 次成功交接；多个阶段仅取得一条新的项目目录/上下文结果就再次交接。每次切换后，模型常先 `tools.load` 或重新导航，没有推进到资料保存。期间还有 5 次检查点参数修复和 3 次错误目标调用，进一步增加轮次。

输入负担同时增长：第一轮 system 估算约 8508 Token，最后一轮普通工具请求约 31079 Token；用户约束与请求另占约 8085 Token。最后的普通工具请求总输入估算约 50737 Token，使用的是 64000 Token 保守回退窗口。这里描述的是应用估算，不能等同供应商计量，也不能据此擅自扩大模型窗口。

并非已经证明“交接丢失了全部镜头正文”。`agent-task-context.ts:184` 起保留未保存的 workingEvidence，`:273` 起带入新阶段，`:286` 明确要求复用证据、不要重新发现或加载已可用工具。现场镜头也确实各读一次。更准确的问题是：准备阶段开销、模型重复选择和阶段控制未能形成有效的保存流程。现有持久化记录没有每轮完整请求正文，无法仅靠记录精确拆分 system 增长中每类内容的占比。

### 2. 防循环只覆盖正文重读，导航与重复加载漏检

`apps/worker/src/agent-context-budget.ts:8` 的 REREADABLE_TOOLS 包括 library/document/novel/scene/production 正文读取，不包括 `project.get_context`、`project.structure.get`、`tools.load`。`:541` 起只对可识别的相同版本正文证据计数。

这轮 16 个镜头各读一次，不触发相同正文四次保护；重复开销主要发生在导航、加载与交接。检查点 `apps/worker/src/agent-task-checkpoints.ts:68` 起按“非检查点工具成功或失败的审计数量增加”判断有新证据，因此重复目录查询、失败路由也能使下一次交接合法。它不是业务保存进展检查。

`apps/worker/src/agent-provider-tool-gateway.ts:195` 起说明已加载工具继续可用，`:234` 起默认累加选中工具；相同工具再次加载仍返回 tools_loaded，没有针对这种无效准备循环的任务进展保护。不能从 13 个已展示工具的数量反推出写工具已加载；本轮没有写入尝试，因而也不存在“写入被权限或 CAS 拒绝”的现场证据。

### 3. 完成判定不校验本次创建与绑定的交付物

`apps/worker/src/agent-provider-loop-service.ts:3938` 的 completeProviderStep 对小说正文有保存检查。`:4018` 的 sceneAuthoringContinuation 主要检查已发生的场次/镜头提交是否存在未解决错误或分段；`:4752` 起可见它以相关写工具审计为入口。

如果模型从未开始创建资料或写入绑定，上述保护不能证明本次用户要求已经实现。`:4032` 起仍允许无业务写入的普通回复结束，标 completed / read-only。直接讨论和查询需要允许只读结束；修复不能把所有普通会话都强制变成写入，也不能用固定关键词替模型理解用户意图。应由明确的任务交付项与对应 Worker 回执判断动作任务是否完成。

本轮最终取消，没有经过成功完成分支。因此这是已确认的机制缺口，不能说它直接把本轮 cancelled 改成了 completed。

`apps/worker/src/agent-generation-preparation.ts:29` 的默认 document.list 会产生 document-query 元数据，但本轮授权清单仍有资料提交和镜头更新工具。仅凭该标签不能认定“任务被错误路由为只读，所以无法写入”。

### 4. “生成完成”属于整个会话底部，容易与正在查看的旧任务混淆

`apps/desktop/src/App.tsx:425` 的 generationStatusMessage 根据 generation 状态生成文案；complete 显示“生成完成”，cancelled 显示停止或错误文案，不校验是否交付了角色资料或镜头绑定。

`apps/desktop/src/ChatPanel.tsx:820` 起渲染可滚动的历史消息，`:846` 将 statusMessage 放在消息滚动区之外。因此浏览旧回复时，底部状态也不必属于当前看到的那轮任务。

## 建议修复顺序（未实施）

1. 用这类“16 镜读取 → 创建三类资料 → 按实际出镜需求绑定”的真实任务形状建立离线回归，包括模型反复导航/加载、不直接写入、检查点参数错误及取消。
2. 整理阶段输入和工具加载策略；复用已取得的资源地图、工具集合及未保存工作证据。阶段切换应为后续业务动作释放可用预算，不因一次重复导航反复交接。
3. 补齐任务级无效准备循环识别，区分新的目标/版本/分页证据、真实保存与单纯重复导航/加载/失败调用；不把交接本身算成业务进展，不简单放宽阈值。
4. 为明确的动作任务记录交付项，以成功回执验收资料创建、真实文档 ID 与逐镜引用；不允许只表达“接下来创建”就报告动作完成。查询、讨论与缺少能力的动作需有准确结果状态。
5. 将任务结果绑定到对应消息，区分“回复结束”“产物已保存”“部分完成”“已取消/未执行”；导航、加载、交接成功不应冒充资料制作完成。
