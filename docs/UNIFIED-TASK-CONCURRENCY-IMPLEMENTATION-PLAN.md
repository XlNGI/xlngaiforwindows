## 1. 目标、基线和计划边界

目标是让所有适合并发的业务拥有独立任务身份，按依赖、资源冲突和容量运行；任务的生命周期与当前显示的项目、会话和组件分离。有依赖的步骤仍等待，同一 SQLite 连接的短写事务仍顺序提交。

计划制定后，用户已于 2026-10-17 指示实施。依次推进各阶段，保留已确认规则及用户已有变更；真实付费调用不在本次实施范围。计划中的模块名、接口和表名为设计名称，编码时优先扩展已有实现。

## 2. 需要明确的产品行为及建议默认值

已确认范围是“都可以并发”。本轮根据用户实施并持续推进的授权，采用下表建议作为实现默认行为；这不是对历史行为的推测。表中规则已经在对应阶段落地并验收，用户后续可明确调整。

| 编号 | 行为 | 建议默认值 | 最晚定稿 |
| --- | --- | --- | --- |
| D1 | 同会话新消息如何执行 | 用户界面只发送原始消息；LLM 在正常 Agent 轮次通过结构化路由选择独立、已完成任务跟进或补充活动任务。Worker 只校验和执行，不在模型判断前建立依赖；独立任务仍受容量与写冲突限制 | P4 |
| D2 | 项目切换、关闭 | 激活另一项目只换界面；显式关闭项目停止该项目本地执行并安全卸载，已接受的远端任务记录为待回查，不重复提交 | P2 |
| D3 | 停止 Agent 回复 | 默认只停止该轮生成；已独立提交的后台子任务继续，另提供明确的“取消此任务及子任务”；取消传播范围由冻结的父子关系决定 | P3 |
| D4 | 依赖何时满足 | 内容依赖按业务声明：可明确使用 draft，但需要正式参考链时必须 approved/published；不得把“已生成”统一当成“可用于生产” | P1/P5 |
| D5 | 重启恢复 | 自动恢复有持久化远端 ID 的查询和可幂等本地步骤；流式文本标记中断并保留片段，需显式继续；未知付费提交不自动重发 | P1 |
| D6 | 后台项目重新加载 | 仅恢复本应用先前登记且用户启用恢复的本地项目；路径不存在、项目身份不符或写锁不可得时等待处理 | P2 |
| D7 | 容量与资源占用 | 采用第 8 节保守初值，保持现有项目 Agent 上限 2；达到后台项目上限时排队或明确提示，不取消已有任务腾位置 | P1/P2 |

“补充任务”先作为明确关联的待处理输入保存，在该任务可接收的轮次边界消费；不改已经发出的 Provider 请求。首版不承诺任意时刻实时改写在途任务。

## 3. 领域不变量

| 编号 | 任何交错顺序下都要成立 |
| --- | --- |
| I1 | 一个任务绑定一个可信项目容器和领域 owner；显示哪个项目不决定写入哪个项目 |
| I2 | 回调必须匹配有效 runtimeEpoch、dispatch/attempt 和任务版本；关闭、取消或被替换的运行没有提交资格 |
| I3 | 每项领域业务只有一个状态权威；调度记录不另行宣布生成、审核、发布或计费成功 |
| I4 | 一个调度阶段只有一个有效认领者；重复唤醒、请求和回调不会重复提交外部副作用 |
| I5 | 写入继续检查 documentVersionId/rowVersion 等领域基线；冲突结果保留，不静默覆盖 |
| I6 | 依赖消费指定产物及其不可变版本；未满足约定里程碑时不能执行下游 |
| I7 | 取消一项任务不清空其他任务的连接、确认、容量或 UI 状态；排队取消不调用 Provider |
| I8 | 远端接单结果未知不能被标为未发送或成功；没有可验证的幂等/回查支持时不自动重提 |
| I9 | 业务队列、运行上下文、网络请求、本地 IO/CPU 和事件缓存均有界；不在等待网络期间持有 SQLite 写事务 |
| I10 | 数据库与文件按明确协议提交；导出快照缺文件或校验失败必须明确失败，不能假成功 |
| I11 | 任务事件按持久化序号关联；时间戳相同、事件重放和订阅切换不改变业务归属 |
| I12 | 进程退出后只恢复声明可恢复的阶段；流式片段和模拟测试通过不等于正文完整或真实生成成功 |

## 4. 项目运行上下文：先完成后端，再开放跨项目界面

### 4.1 生命周期结构

```text
进程级共享：NativeProviderBridge / 网络准入 / AppSettings / 调度容量 / 项目登记
                                      |
                          ProjectRuntimeRegistry
                         /                      \
              项目 A Runtime                 项目 B Runtime
              独立数据库/写锁                 独立数据库/写锁
              独立服务实例                    独立服务实例
              独立调度记录/epoch              独立调度记录/epoch
                         \                      /
                            当前界面订阅项目
                      只选择显示，不拥有业务执行
```

在同一 Node Worker 内建立运行上下文集合，不额外引入常驻 OS Worker 或微服务。每个上下文优先复用一个现有 `ProjectService` 实例及其服务组合；所有项目服务的 `access()` 都绑定该实例，不在回调时查询全局当前项目。

逐步把 `handler.ts` 的模块级单项目服务组装抽成工厂；AppSettings、Native Bridge、外部请求额度和跨项目容量保持进程级。避免每个项目各自创建一套“全局”网络池或覆盖同一最近项目文件。

运行上下文状态为 `opening → ready → draining → closed`；异常进入 `unavailable`。关闭前阻止新认领，取消/隔离活动执行、持久化恢复点、撤销 runtimeEpoch 后，再 checkpoint、关闭连接并释放项目锁。不得先关连接再等待后台回写。

### 4.2 三类代次的职责

| 字段 | 生命周期 | 用途 |
| --- | --- | --- |
| `runtimeEpoch` | 每次可信加载项目生成；关闭或 Worker 重启失效 | 后端服务、工具授权、Native 回调和提交隔离；迁移期沿用现有 projectSessionId 的后端语义 |
| `viewEpoch` | 每次激活/重新订阅视图更新 | 仅控制 UI 是否接受结果，切换视图不撤销仍有效的 runtimeEpoch |
| `dispatchId / dispatchEpoch` | 每次阶段认领或恢复变化 | 拒绝旧执行/旧尝试回调，独立于 Provider step 和业务生成 ID |

稳定 projectId 与资源 ID 只用于定位。写入仍需有效运行上下文、可信路径、项目写锁、任务归属、有效执行代次、未取消状态和领域版本校验。

### 4.3 路由、路径和关闭边界

- 新任务命令显式传项目作用域；Worker 从可信运行注册表解析上下文。模型不能传任意目录让 Worker 打开或写入。
- 旧 UI 命令只用于活动项目；请求入队之前冻结项目和 runtimeEpoch，避免 A 的排队请求在激活 B 后落到 B。生命周期命令走注册表控制通道。
- 新增“激活项目”与“卸载项目”语义，保留原 `project.open/close` 的兼容实现直到旧调用迁移并通过测试；不能在一半入口仍依赖旧全局 current 时提前改变它。
- 同一 projectId 对应两个不同真实目录、目录被移动、联接指向变化或容器身份不符时，不自动选择路径。拒绝同时作为同一可写运行加载，要求明确定位；恢复副本不得静默接管原任务。
- 应用库只登记恢复所需的项目标识、受控路径和用户恢复选择，不存任务正文、产物或检索索引。注册信息丢失可重新定位，项目库任务账本仍是权威。
- 后台 runtime 仅在有任务、确认、订阅或恢复需求时保留；设上限及空闲释放。达到上限时不隐式关闭仍有任务的项目。

## 5. 状态归属、持久化与合同

### 5.1 谁拥有状态

| 对象 | 唯一权威 | 调度层的职责 |
| --- | --- | --- |
| 文本流、Provider step、Token 与生成终态 | 现有 GenerationService / Pi / Agent 领域记录 | 决定何时启动、等待什么和由谁执行，不重复存一份生成终态 |
| 图片/视频任务、远端 ID、提交未知、素材产物 | 现有媒体 job 与结果表 | 以 owner 引用接入阶段调度，查询时映射领域状态 |
| 配音台词、take、job/step、采用结果 | 现有 DubbingService/Repository | 调度独立片段与合成，不改写采用与计费事实 |
| 文档审核、发布、章节锁、结构变更 | 现有领域表及 CAS | 等待领域里程碑；调度完成不能自动审核/发布 |
| 新的完整项目导入/导出任务 | 尚无等价持久化 owner 时，增加文件任务记录，持有清单、目的地和完成/失败事实 | 调度记录只引用该 owner；不为已有 Markdown 导出再建重复实体 |
| 队列、认领、容量等待、重试时点、取消请求 | 新调度记录 | 持久化和恢复这些调度事实 |
| 跨任务依赖和不可变产物绑定 | 项目库依赖/引用记录，FK 指向领域对象 | 计算就绪条件并固定消费的版本 |
| 统一任务日志 | 从调度记录和领域记录投影 | 显示来源状态，允许短暂“正在对账”，不独立写入业务成功 |

调度状态仅表达 `pending / ready / claimed / executing / waiting / reconciling / settled`；`waitReason` 区分 dependency、capacity、remote、confirmation、review、conflict、pause、retry、project-unavailable。终端显示的 succeeded、failed、cancelled、submission_unknown 等由领域 owner 与调度事实计算。

特别规定：`waiting_review`、`conflict`、`paused` 和 `submission_unknown` 都不能被简化成失败或成功。等待审核时释放执行容量，但保留既有章节保护；依赖可以等待审核或明确消费草稿。

### 5.2 最小接口草案

```ts
type BusinessOwner = {
  kind: 'agent' | 'image' | 'video' | 'dubbing' | 'export' | 'import';
  id: string;
};

type TaskRef = { projectId: string; taskId: string };

type ResourceBaseline =
  | { kind: 'document'; id: string; baseVersionId: string | null; expectedRowVersion: number }
  | { kind: 'chapter'; id: string; documentId: string; baseVersionId: string | null; expectedRowVersion: number }
  | { kind: 'scene' | 'shot'; id: string; expectedRowVersion: number }
  | { kind: 'asset' | 'audio'; id: string; contentHash: string };

type DependencySpec = {
  upstream: TaskRef;
  outputSlot: string;
  milestone: 'produced' | 'approved' | 'published' | 'adopted';
  allowDraft: boolean;
};

// Worker 可信创建；不直接接收模型提供的路径、权限或任意 owner。
interface ScheduledTaskView {
  ref: TaskRef;
  owner: BusinessOwner;
  parent?: TaskRef;
  ownerAttemptId?: string;
  scheduleState: string;
  waitReason?: string;
  domainState: string;
  revision: number;
}
```

`taskId` 是统一查询身份，`owner.id` 是原有领域身份；映射唯一，已有 taskId 可直接复用时就复用。`dispatchId` 是调度执行资格，不能冒充 llm attemptId 或 remoteTaskId。媒体选择、付费确认仍使用现有独立 token 并绑定 owner。

新任务类型由代码白名单注册执行器。Agent 仅提交业务意图、候选目标和依赖，Worker 验证真实项目结构、权限、Schema 与无环约束后创建记录；不新增依赖关键词的业务路由。

### 5.3 项目库增量记录

候选表按职责划分，实施时可合并等价现有结构：

| 候选记录 | 必要字段/约束 |
| --- | --- |
| `task_schedule_entries` | project/task ID、唯一 owner kind/id、parent、operationKey/hash、调度状态/等待原因、priority、nextEligibleAt、rowVersion、cancelRequestedAt |
| `task_dispatches` | dispatch ID/代次、task FK、stage、runtimeEpoch、ownerAttemptId 引用、claimedAt/deadline、effectStartedAt、终止记录；同 task/stage 最多一个有效认领 |
| `task_dependencies` | 上游 task/outputSlot、里程碑、草稿策略、失败策略；同项目 FK、去重、自依赖拒绝、环检测 |
| `task_artifact_bindings` | 下游输入槽与上游不可变产物版本/内容 hash 的绑定；不复制文档正文或图片 |
| `task_schedule_events` | task 内递增 sequence、revision、dispatch ID、事件类型及脱敏摘要；状态变更同事务写入 |
| 冲突结果引用 | 优先复用现有 partial artifact/不可变版本；确实不足时增加独立待合并产物引用，提交冲突不能使模型结果丢失 |

项目业务写入、owner 引用、幂等预留及调度事件应尽可能在同一项目事务内完成。暂时不能原子接入的旧入口采用可重放的 owner 对账，不能先产生外部副作用再凭内存补账。

应用库项目恢复登记仅为查找索引；不要求应用库与项目库跨库事务。用项目侧登记事件和启动对账修复索引缺失，不以应用库缓存判定任务成功。

### 5.4 IPC 与兼容

新增版本化能力建议为 `task.schedule.capabilities/create/get/list/events/cancel/retry`，项目生命周期能力为 `project.runtime.attach/activate/list/unload`；最终名称在合同阶段与已有 `project.task.subscribe`、`task.log.list` 合并去重。

- 创建长任务只返回已接受的 taskRef 和 revision，界面通过事件/快照观察；不等待整段生成或复制。
- 每个查询/控制命令包含 projectId 与 taskId；控制操作校验有效运行身份和任务版本。跨项目汇总只返回有权访问的摘要。
- events 使用 cursor/sequence 分页，支持重复投递与断线补播；批量观察避免每个任务多条 250/300 ms 轮询叠加。
- 原 `agent.run`、`image/video.generate.*`、`dubbing.*` 保留领域合同；新路径包裹调度并返回映射。旧兼容入口只允许一个执行 owner，不能与新调度器同时启动同一 job。
- 付费 `requestSubmission/confirmSubmission` 不因统一调度而变成自动批准；过期确认需重新展示并复核冻结参数。
- 确认授权绑定参数 hash、Provider/模型、操作身份和有效期；批准后排队超过有效期或冻结输入发生变化，发送前重新请求确认。不能把“以前批准过”当成无限期付费许可。

## 6. 原子认领、提交、取消与恢复协议

### 6.1 调度与认领

1. 校验运行上下文 ready、项目可写、任务未取消、依赖满足和目标可用。
2. 进程调度器在同一次同步临界区预留本阶段容量；按项目轮转加等待老化选取，避免一个批次占满全局。
3. 通过项目短事务 CAS 领取 task/stage，写入 dispatch、rowVersion 和事件。失败则立即释放预留；成功提交后才启动执行器。
4. 外部请求前持久化提交意图/原有幂等身份。若进程此时退出，恢复按“可能已发送”处理，而不是当作从未发送。
5. 到达远端等待、人工确认或审核阶段时释放无关容量，并持久化下一可执行动作；阶段切换不得持有旧容量等待新容量。
6. 定时器和事件只负责唤醒；每次执行都重新检查账本。重复唤醒不产生第二个执行者。

单 Node Worker 内容量由进程调度器统一拥有；SQLite 持久化认领用于去重、崩溃对账和排除陈旧执行。租约到期不自动表示旧付费请求可以重发，必须先执行恢复策略。

### 6.2 结果提交

回调进入领域服务前核验 task/owner、runtimeEpoch、有效 dispatch、ownerAttempt、取消状态及领域基线。领域写入、产物绑定、事件和调度阶段完成在同一项目事务内推进；文件先写独立暂存区，验收后原子落盘并保留失败补偿。

同目标并发生成允许产生候选结果，但领域提交遵守现有章节锁和 CAS。首版不改变同章一个活动写任务的规则；需要同章多个候选时作为独立候选产物生成，显式合并后再提交正式目标。

版本冲突进入待合并状态，记录原基线、当前版本及本次候选，释放执行容量；不静默改基线重试、不自行合并、不覆盖用户编辑。

### 6.3 取消

- 持久化取消意图及代次撤销，再发 Abort/远端取消；返回本地取消结果，不把远端取消成功作为唯一完成条件。
- 结果提交与取消竞争同一事务/CAS：结果先提交则保留成功，取消先成立则旧执行不能提交。终态结果不被迟到取消改写。
- 只取消排队任务时没有任何 Provider 调用；执行器与容量最终释放必须校验 dispatch 身份，旧 finally 不能释放新任务名额。
- 子树取消按关系与策略逐项记录。共享依赖、被其他任务使用的上游及已完成产物不盲目级联删除。
- 对付费已提交且无法远端取消的任务，区分“本地停止观察/提交”与“远端仍可能执行”；保留 remote ID/unknown 事实和后续对账入口。

### 6.4 恢复矩阵

| 中断点 | 恢复动作 | 禁止行为 |
| --- | --- | --- |
| 未认领、未发送 | 重新进入就绪/等待队列 | 假装已经执行 |
| 文本流中断 | 保留已落盘片段，标记 interrupted；显式继续创建受控新尝试 | 自动承诺无损续写、自动发布 |
| 提交前确定未发送 | 按策略重试并保留操作幂等身份 | 无界重试 |
| 已有远端 ID | 重新绑定新 runtime 下的受控查询执行，只查原 ID | 再提交计费生成 |
| 已发送但无远端 ID | 支持幂等键或 client ID 回查才按适配器策略恢复，否则 submission_unknown | 仅因租约/请求超时重新付费提交 |
| 下载或本地处理 | 核验冻结输入、临时文件及 hash 后重做可幂等阶段 | 无条件采用残缺文件 |
| 文件已发布、数据库未登记 | 依据提交日志/清单核对补登记或补偿，无法证明则报错 | 仅凭存在文件宣布成功 |
| 人工确认/审核中 | 从领域记录恢复卡片；失效 token 重新申请 | 自动批准、静默延长期限 |
| 冲突或暂停 | 保持等待，恢复视图与候选产物 | 自动越过冲突或恢复付费请求 |
| 项目缺失/只读/新版本 | 等待明确定位或写权限，不启动执行 | 向当前另一个项目落盘 |

恢复必须先对账再领取。心跳只辅助发现问题，不能用同线程定时器证明 Worker 卡顿或旧网络请求已停止。

## 7. 依赖、资源冲突与上下文

### 7.1 依赖绑定产物，而非只绑定“任务完成”

依赖边明确 outputSlot、满足里程碑、允许草稿与否，以及失败/取消政策。上游结束但缺少必需产物仍不满足依赖；审核拒绝会阻塞依赖正式结果的下游。

输入分两步冻结：登记时保存用户原始输入、已有版本及待解析产物引用；依赖满足时，在认领下游之前原子绑定真实产物版本并保存输入清单。开始后不随上游重生成或“最新版本”指针改变。

用户主动重新生成通常创建新业务任务；已有下游继续绑定原产物，除非用户明确重建下游。初版只支持同项目 DAG，跨项目只能经过显式导入/复制形成当前项目内资源。

现有 TaskPlanService 复用依赖校验与步骤 CAS 思路，但当前 deliverable 的 kind 唯一约束不能直接表达任意数量的章节/角色图节点；新跨任务边使用 task/slot 身份，不通过重复 kind 强行扩容。

### 7.2 资源协调范围

| 资源 | 协调方式 | 持有时间 |
| --- | --- | --- |
| 文档/章节基线 | 不可变输入版本、现有活动章节保护、短提交 CAS | 不持 SQLite 写事务等待模型 |
| 场次/镜头结构与排序 | 目标行及受影响父容器版本；多资源按稳定 key 排序领取 | 仅领域提交临界区 |
| 素材移动/删除/清空缓存 | 文件租用或保留清单、引用校验、补偿 | 限于确有需要的文件使用阶段 |
| 项目导出 | 备份数据库的引用清单与文件校验；不足时明确失败 | 长复制不持数据库写事务 |
| 项目迁移/卸载/恢复 | 项目生命周期独占门禁，停止新认领并排空/隔离旧写入 | 仅该项目，不阻塞其他项目 |
| 应用设置、Provider 配置 | 应用级短写序列及配置快照/版本 | 不因某项目切换被替换 |

多个资源必须统一排序或使用 try-acquire 后整体退回，避免循环等待。文件 lease 不等于 SQLite 写锁，数据库事务也不能保证磁盘文件快照一致。

### 7.3 同会话消息边界

- 每个运行冻结 `inputMessageId`、历史截止序号和允许继承的分支/已完成回复 ID；不依赖时间戳推断顺序。
- 并行新任务排除其他活动分支的临时输出；有意基于上一任务结果继续时建立明确依赖。
- 普通跟进排队消息不提前生成基于未完成历史的上下文；前序满足后再冻结其依赖输出，用户仍可取消或转为独立任务。
- 对话检索也要遵守运行内可见性：当前任务不能通过 library.search/read 重新读入它本应排除的其他活动分支临时输出。
- 资料正文继续按需检索；可见性约束与版本引用不能成为自动注入全文的新入口。句柄仍按 project/runtime/task/attempt 隔离。

## 8. 容量、供应商和性能

以下为待验收的初值，均可收紧；不是对当前代码能力或用户配置的声明。

| 容量 | 建议初值 | 说明 |
| --- | --- | --- |
| 待执行队列 | 每项目 32，应用合计 128 | 包含依赖/容量/重试等待；超额明确拒绝登记或提示拆批，不能只限制网络队列 |
| 已加载项目运行上下文 | 应用最多 4 | 运行/确认保留引用，空闲可卸载；不自动牺牲旧任务 |
| LLM 在途请求 | 应用 4，每项目最多 2 | 遵守已确认小说计划的项目 Agent 配额并补齐入口验证；仍服从 Native 同 origin 3 和全局网络限制 |
| 独立只读工具 | 每运行 4，进程另有总上限 | 本地同步 SQLite 不因该值获得多线程并行 |
| 媒体提交请求 | 应用 2 | 同步生图直到响应结束占请求额度；异步视频获得 ID 后释放 |
| 视频轮询 | 先保留应用总并发 2、最小间隔 500 ms | 多项目不能各自复制一份全局额度；迁移现有轮询 owner |
| 下载 | 应用 2 | 配合字节、内存和磁盘空间预算，不只数任务 |
| FFmpeg | 应用 1 | 验证机器负载后再调整 |
| 大文件导入/导出 | 应用 1 | 短元数据操作不排在长文件复制后 |

调度阶段只申请实际所需容量。父任务等待子任务时释放执行槽；不能让父任务占满 LLM 槽后等待同池子任务，造成饥饿或死锁。退避等待、人工确认和审核不占网络/CPU 许可。待审核产物不计入待执行队列，避免未审核草稿占满后永久挡住新任务；它们受独立的产物存储配额、章节锁和保留期限控制。人工确认及未确定远端结果设置独立有界等待项配额，并在合同阶段列明与项目 Agent 配额的计数关系，不能用网络在途数代替业务活动任务数。

Rust 与开发 NetworkAdmission 保持各自传输职责；业务池不持有 Native permit 再等待另一业务池。发生未发送的准入拒绝可有界重新排队；对已发送未知状态不得采用同一重试规则。

供应商能力按实际 API 声明并测试：幂等键是否被真正传递、按 remote/client ID 查询、远端取消、同步/异步提交、可重试错误。默认不假设中转网关提供上游幂等。

性能验收记录事件循环延迟、队列等待、在途数、首 Token、确认滞留、恢复时间与磁盘/内存峰值。`cpSync` 等长操作改为可取消的异步流或受控本地处理；SQLite 重查询优化依据测量，不引入第二个未协调的项目写者。

## 9. 分阶段实施

阶段按依赖顺序推进，每阶段完成后记录变更摘要、失败路径、测试证据和遗留项。实际状态见第 12 节；实施授权来自后续用户指令，不从外部参考文件推定。

### P0：先修两处已复现竞态

**P0a 导出一致性。** 先新增正确行为回归，复现“数据库备份完成后、文件复制前删除素材”。最小实现从导出的 SQLite 快照生成完整持久化文件清单，向本次独立暂存目录复制并校验 hash/大小，成功后才发布可用导出。引用文件缺失/变化则明确失败并仅清理本次自建临时文件；允许用户重试，不为了确保成功长期阻塞项目编辑。

清单覆盖图片、视频、独立音频、需要恢复的回收站文件和其他可迁移持久化引用。临时生成缓存、确认 token 和临时签名 URL 不作为可重放运行输入输出。导出副本的任务记录需标识为快照历史；在运行接管设计完成前不能自动重放其中的付费操作。

**P0b 回调归属。** 为制作提交捕获项目运行身份、目标、提交 ID 和 viewEpoch；所有 await 返回、catch 和 finally 写 UI 前校验。覆盖项目 A→B→A、同项目换场景、换镜头、旧请求晚于新请求完成。仅更换视图不应使旧 finally 清掉当前 busy 或确认。

| 项目 | 范围 |
| --- | --- |
| 主要文件 | `project-service.ts`、`image-generation-service.ts`、音频/导出引用枚举、`worker-commands.ts`、`ProductionPanel.tsx`、App 传递的运行身份及对应测试 |
| 合同/迁移 | 优先无 schema 迁移；可增加内部导出清单及 UI 观察身份。不能为省合同改动仅比较 projectId |
| 兼容 | 保持导出目标覆盖策略、素材删除规则、原任务落盘与付费确认 |
| 退出/回滚 | 缺文件明确失败；不得恢复旧“返回成功但不完整”的路径。功能开关不能关闭此正确性修复 |
| 验收 | 两类正确行为用例先失败后通过；成功导出重新打开并执行完整性/文件引用校验；现有素材、配音导出及 ProductionPanel 测试通过 |

### P1：单项目调度最小闭环，接入真实视频业务

在现有单项目生命周期下，先建立调度记录、唯一 owner 映射、原子认领、最小依赖/产物边、容量、取消、事件和启动对账。第一个执行器包裹真实 `VideoGenerationService + MediaOrchestrationService + ProjectTaskRuntime`，使用模拟 Native Provider 验证，不能只做模拟 executor 框架。

直接 UI 创建视频与 Agent 媒体工具准备的视频均映射同一领域 job；Provider/model 和付费批准仍走现有流程。统一观察身份接入现有任务日志。选择开关后，旧轮询器或新调度适配器只能有一个 owner；复用原轮询与下载领域方法，不另写视频生成状态机。

| 项目 | 范围 |
| --- | --- |
| 主要文件 | Contracts/Domain、项目 schema/database/repository、`handler.ts`、`worker-commands.ts`、媒体编排与视频运行、任务日志投影；新调度服务/执行器适配器 |
| 迁移 | 下一可用项目迁移，增加调度及引用记录；只为已有 job 建 owner 映射，不为历史终态任务创建待执行项 |
| 核心门禁 | operationKey+规范化 hash 幂等；重复 dispatch；队列上限；取消/提交 CAS；依赖失败/取消；重启后只回查原远端 ID；旧 dispatch 不能提交 |
| 真实闭环 | prepare → 用户确认 → 排队 → 受控提交 → 保存远端 ID → 轮询/下载 → 原业务入库 → 统一查询/事件 |
| 并发证据 | 用屏障控制两个真实 job 的模拟 Provider 调用，证明执行区间重叠；依赖 job 在产物满足前调用次数必须为 0 |
| 兼容/关闭 | 关闭新任务入口后既有在途任务仍由当前 owner 完成或对账，不能把同一已提交任务交给两套轮询；禁止盲目重提 |

### P2：多项目后端运行上下文与明确路由

建立第 4 节 runtime 注册表和项目服务工厂，将现有全局 current 依赖逐项收敛；先通过直接 Worker IPC 验证 A/B 项目并发，再开放前端切换行为。

| 项目 | 范围 |
| --- | --- |
| 主要文件 | `project-service.ts`、服务组装、`handler.ts`、`worker-commands.ts`、所有项目服务入口的上下文绑定、Native 消息身份、Contracts、AppSettings/Persistence |
| 应用库迁移 | 下一可用版本增加最小项目恢复索引及选择；项目任务正文/依赖不搬入应用库 |
| Native 衔接 | 回调路由依 runtime/task/request 身份；保留原凭据和路径校验，原 projectSessionId 在兼容期代表 runtimeEpoch |
| 生命周期 | activate 与 unload 分离；单项目迁移/排空不停止其他项目；上下文数、句柄和资源有界 |
| 验收 | A/B 同时运行、写各自数据库；排队请求不因激活变化串项目；A 卸载不影响 B；重开 A 拒绝旧 epoch；同 ID 不同路径/只读写锁/路径移动正确处理 |
| 兼容/关闭 | 新入口关闭后停止接纳额外 runtime，逐个安全排空；不能把多个活跃项目硬塞回单 current 模型或直接关连接 |

P2 不以“改完几个 React state”判定完成。若任何有副作用的项目入口仍在 await 后使用全局 current，跨项目运行门禁保持关闭。

### P3：前端多任务观察、独立确认与取消

将 generation/nativeRun/taskPolling/busy/confirmation 移为按 taskRef/generation ID 管理的运行集合；组件只订阅。切换项目/会话不调用业务取消；Worker 已拥有的 Pi loop 不因 UI 观察断开而自动终止。

| 项目 | 范围 |
| --- | --- |

P3 保留项目关闭与应用退出的明确行为，不把用户显式卸载项目解释成普通界面切换。

### P4：同会话任务分支与独立只读工具并发

先落实 D1 和第 7.3 节消息边界，再协调修改前端发送门禁、后端事务互斥和恢复观察。以每运行配额、分支可见性、独立授权及目标保护提供等效替代，相关检索计划 C1 同步变更。

工具只开放已证明独立的只读组。Gateway 对同一 Provider 响应先冻结调用与授权集合，完成该组后统一计算下一 definitions；不能让并发回调各自整体覆盖 definitions。含写工具的组继续按合法顺序运行。

| 项目 | 范围 |
| --- | --- |
| 主要文件 | `generation-service.ts`、`context-service.ts`、`library-search-service.ts`、Pi Runtime、工具 Gateway/Loop/Registry、消息 repository/分支引用、App/ChatPanel |
| 迁移 | 下一可用项目迁移保存消息序号/分支边界、输入与源运行引用；旧记录按显式兼容分支读取，不伪造历史关联 |
| 授权 | task/attempt/Provider step 本地授权、预算预留、Provider call 去重和审计保持有效；不改全部工具为 parallel |
| 验收 | 同会话两项独立运行真正重叠；普通跟进按依赖等待；跨分支临时输出不可见；同工具多调用预算正确；取消不损坏另一项授权 |
| 兼容/关闭 | 关闭后新同会话请求回到单轮接纳；已有分支继续展示并完成，不合并历史或重发任务 |

普通写工具在单个运行内部仍可串行，但不同任务处理不同资源可以并发生成并分别提交。只有明确需求且通过独立授权验证后才扩展同一 Provider step 内的多写并行，不把它作为“全系统并发”的必需条件。

### P6：恢复、压力、迁移与完整质量门禁

恢复不是到 P6 才实现；P1/P2 已有最小恢复门禁。P6 扩展跨任务、跨项目及系统退出的组合故障验证，执行完整发布前检查。

- 重复 IPC、乱序/迟到回调、取消与提交竞争、恢复与旧执行重叠、确认过期、用户手动修改、磁盘不足、数据库/文件故障注入。
- 进程退出发生在认领前后、提交意图落盘后、远端 ID 落盘前后、文件发布与领域登记之间；每个点都能对账且不盲目计费重提。
- 队列满、后台项目上限、同 origin 限流、父子同池等待、长时间审核、项目只读和应用设置变更；各项目有公平进展，无新全局串行热点。
- 全仓质量检查、Rust、Sidecar、NSIS 打包以及实际 Windows 多窗口/切换/休眠恢复验收。真实付费样例单独授权；模拟测试不替代真实账号和质量验收。

## 10. 数据库迁移、开关与回滚

### 10.1 迁移清单

| 阶段 | 项目库 | 应用库 | 原有数据处理 |
| --- | --- | --- | --- |
| P0 | 默认无迁移 | 无 | 导出清单内部版本；不改变用户业务内容 |

| P2 | 如需持久化 runtime/登记版本则增量增加 | 项目恢复索引、选择及位置版本 | 不复制项目任务/索引，不自动加载未知目录 |

每次迁移先重新核对代码版本和其他在途计划，分配唯一版本号；新库直建、v49 升级、当前各过渡版本、重复迁移、迁移失败回滚均要测试。升级前 checkpoint、一致性备份、quick_check 和 foreign_key_check；失败不留下半升级库。

### 10.2 关闭能力与数据回滚分别处理

每阶段有能力开关用于阻止新接入；在途执行继续由已认领 owner 完成或对账。禁用调度不能回退为不受限付费重试，不能删除队列、运行记录或候选产物。

Schema 升级不能承诺旧二进制直接打开。需要回退旧版本时使用升级前备份，并先登记升级后已接受的远端任务；不能因为恢复旧库丢了 remote ID，就认为远端未提交。跨版本接管不清楚时保持等待并人工对账。

P0 的正确性修复不设置可关闭的“恢复缺陷”开关。调度开关与 Provider 模型配置分离，不能静默替换供应商。
